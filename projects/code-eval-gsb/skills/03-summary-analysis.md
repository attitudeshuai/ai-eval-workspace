# GSB 汇总分析 · 评价汇总表单生成

> 配置从 `../config.toml` 读取。
> 依赖 agent：`skills/implementation-reviewer/SKILL.md`、`skills/humanizer-zh/SKILL.md`

所有模型对话完成后的最终汇总。读取各模型的对话内容 + 代码变更，调用 implementation-reviewer 进行专业评审，经 humanizer-zh 去 AI 化后生成评价汇总表单。

## 功能概述

1. 读取所有模型的 `-对话内容.md` 文件
2. 结合对应分支仓库的代码变更，调用 `implementation-reviewer` agent 进行专业评审
3. 调用 `humanizer-zh` agent 对评审文字去 AI 化
4. 生成一份填写完整的标准评价汇总表单

**本技能不负责：**

- 执行模型对话（由用户在 Trae 中手动完成）
- 修改分支仓库的代码
- 代替人工提交最终打分（需人工核对 `【待确认】` 字段）

## 命令

| 命令 | 说明 |
|------|------|
| analyze | 默认命令。读取对话内容 + 分析代码变更 → 调用 implementation-reviewer → 调用 humanizer-zh → 生成评价汇总表单 |
| init | 仅根据已知信息预生成表单骨架，不运行任何 agent，适合模型对话完成前预填固定字段 |

## 默认配置

> 从 `../config.toml` 的 `[analysis]`/`[[models]]`/`[[comparisons]]`/`[paths]` 段读取。关键：8维度评分（5基础+3Add-on）、Bad Pattern 识别、长程任务判定（≥5文件）、GSB 强制二选一。

## 执行流程

### analyze（默认命令）

1. **读取对话内容**：加载所有模型的 `-对话内容.md` 文件，提取：
   - 首轮提示词（含约束标签）
   - 每轮对话的 session id
   - 总交互轮次
   - 「每轮 context 记录」表、是否触发自动压缩、最后一轮 context 占用
   - 是否存在用户手动打断迹象（如用户中断指令、重发 prompt、明显纠偏语句）

   一致性核对：末尾「是否触发自动压缩 / 最后一轮 context 占用」必须与记录表推导一致（任一轮触发即「是」；压缩时 Z 取压缩前最高读数）。不一致或缺失时提示用户补填，不得自行编造读数。

2. **检查代码变更**：对每个模型分支仓库执行：
   ```bash
   git log main..HEAD --oneline
   git diff main
   ```
   判断：
   - 是否有新提交（无提交则代码理解/纯分析类填 N/A）
   - 修改了哪些文件（判断修改范围：单文件 / 模块内多文件 / 跨模块多文件 / 跨系统多模块）
   - PR 链接由用户提前在对话内容中记录，或在 analyze 执行时由用户提供

3. **调用 `implementation-reviewer` agent**：传入以下上下文，分析各模型：
   - 首轮提示词（含约束标签）
   - 每个模型的完整对话内容
   - 代码 diff（如有）
   - 任务类型

   分析 **8 个维度（5 基础 + 3 Add-on）**，每个维度输出：
   - 建议分数（1-5）
   - 出现的问题标签（Add-on 维度多选，标签清单见方案文档第四节）
   - 理由（1-2 句分析支撑，含可定位证据：轮次+动作）
   - GSB 对比结论（按 `[[comparisons]]` 的 3 组 anchor-based 对比）

   Add-on 维度注意：
   - **长上下文保持能力**：仅 context ≥ 200K（≥20% of 1000K）的样本打分；未达阈值评分与问题标签留空、理由填 `N/A`
   - **ToolCall 效率**：需额外记录「出现问题的工具名」

   **评分区分度要求（强制）**：
   - 同一题内各模型的**平均分不得并列**，必须全部拉开
   - 初评出现并列时，回到各模型的轮次评价记录找可定位的差异证据（验证方式扎实度、遗留问题数量与性质、约束摩擦、工具调用冗余密度、自查自修能力等），在对应维度按 1 分粒度拉开分差，禁止为了拉开而拉开
   - 分差方向必须与 GSB 对比结论一致：GSB 胜出方的平均分**不得低于**落败方；若出现倒挂，说明评分或 GSB 结论有一方错了，必须复核修正后再生成表单
   - 拉开分差后需同步更新受影响维度的打分理由，使理由能支撑该分数

4. **调用 `humanizer-zh` agent**：对 implementation-reviewer 输出的**所有评价、备注文字**进行去 AI 化优化：
   - 各模型每个维度的评分理由
   - 打断分析反馈
   - GSB 对比评价
   - 「其它信息备注」中的观察记录

   **所有评价文字必须经过 humanizer-zh 处理后才能写入表单，原始输出禁止直接落盘。** 目标语气：像真实评测员手写的口语反馈。

5. **生成评价汇总表单**：按模板写入 `A-<项目名>-<类型>-评价汇总.md`：
   - 可自动填写的字段（提示词、环境信息、题目标签、session id、交互轮次等）：直接填写
   - 需人工核对或由用户提供的字段（业务领域、操作系统）：填写 `【待用户填写】`
   - 主观评分字段（各维度 1-5 分）：填写 implementation-reviewer 建议值，标注 `【参考值，请确认】`
   - PR 链接：有则填，代码理解类等无代码变更的填 `N/A`

6. 输出文件路径，提示用户核对 `【待用户填写】` 和 `【参考值，请确认】` 字段后提交。

### init

1. 读取类型目录下任意一份 `-对话内容.md` 文件，提取首轮提示词和约束标签。
2. 从项目配置读取项目信息：GitHub 地址、技术栈、任务类型。
3. 预填写固定字段：Prompt、Github Repo、技术栈、任务类型、指令约束、是否长程任务。
4. 其余字段留空占位，输出骨架文件。
5. **不调用任何 agent。**

## 评价模型（0731 期：四个模型各自独立一条，每题必填 4 条）

每条评价的固定格式：首行一句话概括 Bad Pattern（无则写「无明显Bad Pattern 。」；有则写「模式名（具体表现）。」，多个用分号隔开），随后按编号逐个对比**其余每个模型**，格式为「N、与<X>对比：<本模型> 更好/差一点，<结合具体轮次与事实的理由>」。理由必须聚焦**被评价模型自身**的优点或缺点（它做对了什么、留了什么尾巴），不要把篇幅花在描述对比方的表现上。

⚠️ **方向性要求（强制）**：结论说谁好/谁差，理由就只写谁的好/差，对比方不出现在理由里。具体：
- 说 <A> 更好 → 只写 <A> 好的点；**不写** <A> 不好的点，也**不写**对比方好的点（对比方的差同样不写）。
- 说 <A> 差一点 → 只写 <A> 差的点；**不写** <A> 好的点，也**不写**对比方差的点（对比方的好同样不写）。
- 常见错误：「A 差一点。A 整体不错，但某处错了」（混入了 A 的好）、「A 更好。B 在某处错了」（写的是对比方的差）——这两种都不允许。

## 注解

### 1.0 修改范围

| 修改范围 | 说明 |
|----------|------|
| 单文件 | 局部逻辑修改 |
| 模块内多文件 | 涉及同一模块内的接口定义与实现协同 |
| 跨模块多文件 | 涉及多个逻辑单元的调用链修改 |
| 跨系统多模块 | 涉及前后端联调、跨服务调用、或数据库-后端的垂直改动 |

### 2.0 是否为长程任务

任务是否在指令目标明确的前提下，需要模型经历多步规划、跨越多个模块、伴随环境反馈经历多次调试与自我纠错、修改不少于 5 个文件才能完成的大型重构或功能开发任务。如果是，tag 为「长程任务」。

### 3.0 GithubPR

自动将模型在对应分支完成的修改推到 GitHub，提 PR 到 main 分支，把 PR 网址填入。PR 描述写 `<模型>的pr`。代码理解类（无代码变更）填 `N/A`。

### 4.0 评分标准

5 个基础维度，每个维度 1-5 分：

| 维度 | 1分 | 3分 | 5分 |
|------|-----|-----|-----|
| 交付完整性 | 完全失败/严重事故 | 勉强达标，有明显 Bug | 一次性完美跑通，零虚假成功 |
| 指令遵循 | 彻底无视所有约束 | 遵循核心但遗漏 1-2 个显式约束 | 分毫不差，无任何自作主张 |
| 任务规划 | 完全像无头苍蝇 | 有大方向规划但子任务不细致 | 极具 Agent 属性，完美拆解+工具使用 |
| 推理能力 | 对需求理解完全错误/严重幻觉 | 理解主要任务但遇错需 2-3 次修复 | 深刻理解，一针见血定位根因 |
| 边界感 | 擅自删除核心文件/屡教不改 | 有越界但经纠正可改回 | 零越界，危险操作前主动询问 |

另有 3 个 Add-on 维度（长上下文保持能力 / 思考效率 / ToolCall效率），完整 rubric、问题标签清单与填写规范见 [Seed模型 GSB 众测方案（0731）.md](../docs/Seed模型%20GSB%20众测方案（0731）.md) 第四节。

### 5.0 美观度

仅有前端 UI 变更类任务适用。非 UI 类填 `N/A`。

| 分数 | 说明 |
|------|------|
| 5 | 完美复用原有样式规范，布局合理、留白舒适、对齐精准 |
| 4 | 整体良好，有细节瑕疵，用户指出 1 次后能补齐 |
| 3 | 能用但简陋，需明确指令纠正 1-2 次 |
| 2 | 严重结构性问题，2 次纠正后仍调不对 |
| 1 | UI 彻底崩坏，毫无美感与可用性 |

## 注意事项

1. **analyze 命令依赖真实对话数据**：各 `-对话内容.md` 必须由用户在 Trae 填写完模型对话后再执行。
2. **init 命令可在模型对话前执行**：只需有提示词和项目配置即可生成表单骨架。
3. GithubPR 自动推送分支后创建 PR，无变更任务填 `N/A`。
4. 主观评分由 `implementation-reviewer` 提供参考，标注 `【参考值，请确认】`，最终由人工确认。
5. **所有评价、备注文字必须经 `humanizer-zh` 去 AI 化后才能写入表单**，禁止直接使用原始输出。目标：像真人手写的评测反馈，而非报告式措辞。
6. 若目标文件 `-评价汇总.md` 已存在，必须征求用户确认，不得直接覆盖。
7. commit 代码时，commit 信息填 `<模型>`。
8. 表单落盘前自查评分区分度：各模型平均分无并列，且分数排序与各组 GSB 结论方向一致（胜出方平均分不低于落败方）；不满足则回到第 3 步修正评分或 GSB 结论，不得带病落盘。
