# 【0825】Seed模型GSB众测方案 副本

**什么是模型众测？**

模型众测是指在模型迭代的过程中，通过组织代码专家通过真实 Coding 场景任务对 Seed 模型进行系统性评估以验证其实际能力、发现其明显问题或性能退化，从而指导模型迭代优化的过程。

在本期项目中，我们将在Trae SOLO Agent 上 对 **4 款模型**进行 Coding 能力的 GSB（Good, Same, Bad）对比。

# 三、出题要求

为了让众测样本能够深度对齐**模型训练**的**数据多样性**，并确保众测结论的**外部有效性**，我们要求专家出题时，对“什么样的题目出多少道”进行明确的锁定。**出题需按照下述分布执行，允许上下浮动 2%。**

|**代码理解**|解释逻辑、寻找潜在风险、回答技术细节|**5%**|
|**工程化**|环境配置、依赖管理、CI/CD 相关|**5%**|
|**代码测试**|单测、集成测试等|**5%**|

|业务领域|分布|||
|---|---|---|---|

我们不用主观的“难/易”，改用客观的“代码蔓延范围”来定义复杂度。对于代码理解这类无代码生成任务，我们将“修改范围”映射为“代码理解范围”。

|---|---|---|

## 3\.4 用户指令约束

为定向考察模型在 **指令遵循 **上的能力，我们要求专家在题目 Prompt 中 **刻意注入约束条件**。

|**约束标签**|说明|举例|
|---|---|---|
|技术栈或依赖约束|指定**必须**或**禁止使用**的技术栈或工具|“使用 Python 实现”/“禁止引入任何第三方 npm 包”/“pandas 版本为1\.5”/\.\.\.|
|架构或模式约束|指定产物**必须符合或禁止**特定架构或设计模式|“使用单例模式/“必须将 UI 层与逻辑层拆分为两个文件”/\.\.\.|
|代码风格或规范约束|指定代码**必须符合或禁止**某种格式或风格|“变量名必须用驼峰式”/“所有函数必须包含 JSDoc 注释”/\.\.\.|
|非代码回复约束|指定 Agent **必须附带**特定的非代码回复，且必须符合或禁止某种输出格式|“列出模块的名称”/“用 Markdown 输出部署步骤”/“写出核心依赖”\.\.|

|---|---|---|
|**0个标签**|**5%**|考察宽泛意图下模型直觉泛化与默认审美|
|**1个标签**|**10%**|基础对齐能力测试|
|**2个标签**|**35%**|组合约束测试|
|**3个标签**|**35%**|组合约束测试|

## 3\.5 Repo **防同质化限制**

|**限制类型**|**限制建议**|**目的**|
|---|---|---|
|**单 Repo 题目上限**|在一期众测中，**来源于同一个 repo 的题目不应超过总题量的**** 2%**<br>例如：100 题的众测，同一个 repo 的出现次数不应超过 2 次|避免特定repo场景导致模型胜率过拟合|
|**Repo 相似度**|**对于高度同质化的 repo，在计算题目上限时，应合并计算。**<br>- 例如：专家虽然用了两个不同的 Repo，但这两个 Repo 都是基于同一个前端脚手架生成的，里面的实现几乎一模一样，依赖包高度相似。||

## **3\.6 交互约束与轮次限制（三轮）**

**每个任务的交互轮次不超过 3 轮 。**

若模型在首轮中未完成任务，或交付物不满足任务需求，专家可以继续与模型对话，要求或引导模型继续完成任务/修复产物中的问题。但总轮次不得超过 **3 **轮。且在给模型评分时，需要综合模型所消耗的轮次和最终产物质量来进行评分。

**例外情况：**

- 对于**工程故障**（网络波动导致请求失败）导致的需要人为“继续”的情况，不计入轮次。

- 但是，对于**轮次超限**需要人为“继续”的情况，应计入轮次。

## 3\.8 Max模式分布要求（60/40）

**60%****的任务开启 Max 模式，****40%****的任务不开启Max模式。**

**更复杂、更长程的任务开启 Max 模式。**

**在同一个任务（对话窗口）中，必须保持开启或不开启Max模式，不可中途切换。**

**同一个任务，所有横评的模型都必须同时开启或不开启Max模式，不能有的开有的不开。**

**怎么确认 Max 真的生效了：**开启后对话底部的上下文使用率会显示为 `X% of 1000K`。如看到窗口不是 1000K，请立即检查配置并重测

## 3\.9 打断记录说明

「打断」指在模型执行过程中，专家人为中止它当前正在进行的动作，例如点击停止生成，或在模型还在写代码、还在调工具时就插入新指令把当前动作截断。等模型自然结束一轮之后再追加要求，不算打断，那属于正常的多轮交互。

**打断与轮次的关系：**打断之后重新给指令等价于开启新的一轮，因此**打断必须计入 3\.6 的三轮上限**。唯一的例外是工程故障（网络波动、请求失败）导致必须人为点「继续」，这种情况既不算打断，也不计入轮次。

四个模型必须一视同仁：不能只打断其中一个模型，再拿它被截断的产物去和其他模型的完整产物做 GSB 对比。如果某个模型因为明显跑偏或陷入死循环而不得不打断，请在它的评价字段里写清楚，并在对应的基础维度（任务规划 / 推理能力 / 执行能力）和 Add\-on 维度上体现出来，而不是只在打断字段里记一笔。

**交付表中对应两个字段，四个模型（Odysseus / Athena / Poseidon / Cyclops）各一列：**

|字段|类型|填写要求|
|---|---|---|
|**是否打断模型 \- 模型名**|单选|该模型在本题中是否被人为打断，在「有打断」和「无打断」中选一个。|
|**打断分析反馈 \- 模型名**|文本|选「有打断」时必填，需包含：打断发生在第几轮、打断时模型正在做什么、打断的原因（如陷入死循环、大面积改错文件、明显跑偏），以及打断后模型能否按新指令恢复。选「无打断」时可留空。|

# 四、打分方法

### **4\.1 五个基础维度**

以下五个维度涵盖了从结果、过程到核心推理能力以及合规底线的全维度闭环，应为每一期众测的基础打分维度：

|**维度**|**描述**|**5分 \(完美/超预期\)**|**4分 \(优秀/小瑕疵\)**|**3分 \(及格/勉强可用\)**|**2分 \(不及格/需重构\)**|**1分 \(完全不可用/严重事故\)**|
|---|---|---|---|---|---|---|
|**交付完整性 \(Delivery\)**<br>|**任务成败：**需求功能点是否完整实现？代码能不能跑？有无虚假成功（宣称做完了实际没改或改错）？<br>|**一次性完美跑通**。不仅实现了所有明示需求，还主动补全了隐性需求（如边界处理），**零**虚假成功。|**基本完美**。达成所有主要需求，代码可运行，但有极少量的细节遗漏，**无**虚假成功。|**勉强达标**。核心功能可跑，但有明显 Bug 需人工微调；或存在**轻微**的虚假成功（如某非核心文件未保存）。|**未达成主要需求**。代码因逻辑或依赖问题无法运行；或存在**较大比例**的虚假成功（如宣称改了 5 个文件，实际只改了 2 个）。|**完全失败**。代码严重编译报错完全不可运行；答非所问；或出现**极其恶劣**的虚假成功（满口答应但一行代码没写）。|
|**指令遵循 \(Instruction Following\)**<br>|**服从性与约束达成**：模型是否严格遵守了用户在 Prompt 中明确提出的所有约束条件（如：特定库的使用、代码风格、禁止修改的文件等）？|**分毫不差**。完美遵循了所有显式和隐式约束，包括最细微的格式要求。没有表现出任何“擅作主张”的行为。|**基本遵从**。遵循了所有核心指令和绝大部分次要约束，可能在极细微的非关键格式上有一点偏差。|**部分遗漏**。遵循了核心目标，但遗漏了 1\-2 个明确的负面约束（例如：让它别改 A 文件，它还是改了一行注释），需要人工轻微修正。|**违背核心指令**。忽略了关键的约束条件（例如：明确要求用 React，它写了 Vue；或完全无视了禁止使用的库），导致产物需要大规模重构。|**完全失控**。彻底无视用户的所有约束指令，或者反其道而行之。表现出严重的“对齐失败”，产物完全不可用。|
|**任务规划 \(Planning\)**<br>|**Agent属性：**是否能合理拆解任务？是否有清晰的阶段性状态追踪？遇到歧义时是否主动求问？是否有阶段性总结或反馈？|**极具 Agent 属性**。大/子任务拆解极度清晰合理；**完美运用** TodoWrite/Checklist 工具并实时更新状态；遇到歧义**主动**向用户求证。|**规划优秀**。有合理的拆解和总结；大部分时间能正确使用工具并追踪状态；偶有（\<25%）工具使用不规范。|**规划及格**。有大方向的规划，但子任务不够细致；阶段性总结时有时无；工具使用存在明显遗漏（约 50%）。|**缺乏规划**。上来就盲目写代码，无拆解；极少使用工具或状态追踪错误；遇到歧义全靠自己瞎猜。|**毫无规划**。完全像无头苍蝇，没有任何步骤概念；拒绝使用任何工具；任务状态完全不可知。|
|**推理能力 \(Reasoning\)**|**模型"想"的正确性与性价比：**从理解需求、逻辑推导到落地的全过程，是否能准确定位根因并修复，而不是陷入幻觉或自相矛盾。推理所消耗的资源（reasoning token 和思考所花的时间）跟题目难度匹不匹配。|**顶级理解且高度匹配**。深刻理解业务意图与隐性约束；遇到报错能**一针见血**定位根因并一次性修复；逻辑严密无懈可击。简单题快速直达结论，难题思考充分且聚焦根因，无发散、无绕圈。|**逻辑清晰且高效**。方向完全正确，能较快定位报错原因；可能偶尔忽略次要边界条件，但总体推理顺畅。思考总体高效，偶有轻微冗余或一两次自我重述，不影响整体效率。|**逻辑及格**。理解了主要任务但忽略了部分条件；遇到报错时需要尝试多次才能找到正确解法。简单题可能存在**冗余思考**（CoT较长），或难题思考整体偏发散，可完成任务但等待明显变长。|**逻辑混乱**。推理过程犹豫，选择了极笨的非最优解；遇到报错时存在明显的“猜答案”迹象，无法定位根因。可能出现普遍的过度思考或思考不足，可能出现反复自我怀疑，明显低效。|**完全失控**。对需求理解完全错误；严重幻觉；陷入**思考死循环**/长篇发散/自我否定绕圈，思考严重浪费甚至导向错误结论。|
|**执行能力**<br>**\(Toolcall\)**|**模型"做"的正确性与性价比：**模型实现目标的动作（toolcall）路径是否少而准，是否能选对工具、能从报错里恢复；而不是重复读同一文件、反复跑同一个失败命令、选错工具、过度探索、原地打转。|工具调用**精准并且最小化，**没有出现重复读取同一文件、无效探索等问题，能合理批量或并行，ToolCall一步到位|调用基本高效，偶尔有少量的冗余读取/检索等，但不影响结果和整体效率|存在较明显的**冗余调用，**比如多次重复grep/read、文件间反复地来回横跳，最终虽然完成了任务，但整体效率有提升空间|**大量冗余或失败调用**，在文件间反复横跳，工具使用明显低效|工具调用严重滥用或缺失，比如该读的文件不读全靠自己瞎猜，无意义地反复调用工具等，导致任务最后产物完全不可用|

### 4\.2 四个单独评价维度

本期共有以下四个Add\-on维度：

- **边界感**

- **长上下文保持**

- **思考效率**

- **工具调用效率**

每个字段均采用** 出现的Bad Pattern\+ 具体描述**** **的字段组合，理由字段应包含客观事实，不允许只写“还行/不好/一般”这类无信息量的描述。其中**思考效率**和**工具调用效率**应该与基础维度中的**推理能力**/**执行能力**的评分存在一致性，不应有矛盾。

#### **Add\-on：边界感**

> 之前边界感作为一个基础维度，随着模型迭代，彼此之间的差异很小，但一旦出现仍然是破坏性的，因此不再进行1\-5分制打分，而是下降为单选维度，如果出现了边界感的问题，则进行具体描述。下方仍展示之前的打分规则作为参考，但不再打分。
> 
> 

|字段|类型|字段说明|
|---|---|---|
|**Bad Pattern**|单选|* [ ] 未出现边界感问题<br>* [ ] 出现了影响体验的越界问题|
|**描述**|文本|填写该字段时需要包含：<br>1. **可定位的证据****（轮次\+动作）**：比如在第几轮，做了什么动作/哪次工具调用等<br>2. 对**交付或过程的****具体影响**|

# 五、作业流程与交付字段

### 题目设计

- **设计真实场景**：出题贴合线上真实研发协作场景，测试模型的真实业务水位与缺陷

- **明确题目标签**：记录题目在**"出题要求"**一节中，在每个维度上分别属于哪个标签

- **准备测试环境**：确保代码仓库、依赖等可用

### 测试执行与交付

每一道题目，对四款模型分别进行测试。

1\. **创建新对话 **→ 2\. 输入题目 prompt → 3\. 观察交互 → 4\. 记录表现 → 5\. 评估结果

测试后，**及时记录**评估结果与观察到的具体现象，并且提供关键问题的**截图**。
