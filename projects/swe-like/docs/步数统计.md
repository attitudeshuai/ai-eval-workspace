# Trae Session 有效 TC 调用次数自查指南

> 实操抓取顺序（含 Trae 3.3.95 终端命令不落盘的处理）见 `../skills/02-step-count.md`。

本文用于指导 Trae CN 用户根据 Session ID，自查一次会话中有效的 TC（Tool Call，工具调用）次数。

适用环境：macOS、Windows、Trae CN。不同 Trae 版本的日志字段和日志目录名可能略有差异，最终应以 `toolCallId`、`serverCallId`、服务端操作 ID 和实际执行结果交叉确认。

## 1. 先统一统计口径

### 1.1 什么是有效 TC

一次调用同时满足以下条件时，计为 1 次有效 TC：

1. 由 Agent 为完成用户任务而发起。
2. 有可识别的服务端工具调用标识，例如 `toolCallId`、`serverCallId`，或能够与 plan item 对应的服务端操作 ID。
3. 工具实际进入执行阶段，并产生有效结果。
4. 同一个工具调用的多个客户端执行阶段、状态轮询和结果读取只计算一次。

常见有效 TC：

- 创建或修改文件。
- 执行终端命令。
- Agent 主动调用的搜索、读取、浏览器或其他外部工具。

### 1.2 哪些内容不能直接按 TC 计数

- `plan item`：可能是分析、计划、确认提示、工具步骤或最终回复，不等于 TC。
- TS/turn：一次 TS 调用中可以包含多个 TC。
- 流式响应分片：同一个响应可能产生多条 SSE 日志。
- `checkRunCommandStatus`：只是轮询同一个终端命令的状态。
- `getAutoRunConfig`、`getConfigurationValue`：客户端配置读取。
- `getDiagnostics`、`fileDiffCount`、`getDocumentByUri`：编辑器刷新或辅助检查。
- 自动上下文收集：如果批量 `readFile` 没有独立服务端 TC 标识，通常不作为独立有效 TC。

### 1.3 去重示例

- `createFile` + `applyChatSnapshotPatch` 如果对应同一个服务端写文件操作，合并为 1 次 TC。
- `runCommandInTerminal` + 多次 `checkRunCommandStatus` + 最终结果读取，合并为 1 次 TC。
- 同一 `toolCallId` 在多行日志中出现，只计算 1 次。

## 2. 找到 Trae 日志目录

### 2.1 macOS

macOS 上 Trae CN 的日志通常位于：

```text
~/Library/Application Support/Trae CN/logs
```

### 2.2 Windows

Windows 上 Trae CN 的日志通常位于当前用户的 Roaming AppData：

```text
%APPDATA%\Trae CN\logs
```

展开后通常类似：

```text
C:\Users\<用户名>\AppData\Roaming\Trae CN\logs
```

在 PowerShell 中，`%APPDATA%` 不会像 CMD 那样自动展开，应使用 `$env:APPDATA`：

```powershell
$traeLogs = Join-Path $env:APPDATA 'Trae CN\logs'
Test-Path -LiteralPath $traeLogs
Get-ChildItem -LiteralPath $traeLogs -Directory
```

在资源管理器地址栏或 CMD 中，可以直接输入：

```text
%APPDATA%\Trae CN\logs
```

如果上述目录不存在，先确认运行的是 Trae CN，并只读查找当前用户 Roaming AppData 下实际使用的 Trae 目录：

```powershell
Get-ChildItem -LiteralPath $env:APPDATA -Directory -Filter 'Trae*'
```

不同安装渠道或版本可能使用略有差异的产品目录名。找到实际目录后，将下文 `$traeLogs` 的值改为该目录下的 `logs`。

### 2.3 时间戳目录和日志文件

每次启动 Trae 通常会生成一个时间戳目录，例如：

```text
20260901T113220
```

主要检查的文件一般是：

```text
<Trae 日志目录>/<时间戳目录>/window*/renderer.log
```

对应的常见完整路径为：

```text
# macOS
~/Library/Application Support/Trae CN/logs/<时间戳目录>/window*/renderer.log

# Windows
C:\Users\<用户名>\AppData\Roaming\Trae CN\logs\<时间戳目录>\window*\renderer.log
```

一个时间戳目录可能包含多个 `window`。不要只检查 `window1`，应搜索整个 `logs` 目录。

## 3. 推荐方法：把 Session ID 发给 Agent

### 3.1 准备 Session ID

复制完整 Session ID。常见格式类似：

```text
<user_id>:<trace_id>_<session_id>.<agent_message_id>.<user_message_id>:<客户端版本和时间>
```

完整字符串无法直接命中时，Agent 应拆分搜索以下字段：

- `trace_id`
- `session_id`
- `user_message_id`
- `user_id`

其中 `session_id` 通常是定位整段会话日志最重要的字段。

### 3.2 推荐提问模板

将下面的模板和完整 Session ID 一起发给有本机文件读取权限的 Agent：

```text
请只读检查下面这个 Trae CN Session ID 对应的有效 TC（Tool Call）次数：

<粘贴完整 Session ID>

Trae 日志目录通常是：
- macOS：~/Library/Application Support/Trae CN/logs
- Windows：%APPDATA%\Trae CN\logs（PowerShell 中使用 $env:APPDATA）

统计要求：
1. 先识别当前操作系统，并搜索该系统下的整个 logs 目录，不要只查当前工作区或单个 window 目录。
2. 按唯一 toolCallId、serverCallId 或可验证的服务端操作 ID 去重。
3. createFile 与 applyChatSnapshotPatch 如果属于同一写文件操作，只算 1 次。
4. runCommandInTerminal 及其 checkRunCommandStatus 轮询只算 1 次。
5. 排除 plan item、TS/turn、SSE 分片、配置读取、诊断刷新、状态轮询和无独立 TC 标识的自动上下文收集。
6. 只把实际执行并得到有效结果的工具调用计入有效 TC。
7. 输出 TC 总数、每次 TC 的 ID/工具/行为/结果，以及被排除项目和原因。
8. 给出命中的 renderer.log 完整路径及关键日志行号。
9. 不修改或删除任何 Trae 文件，不输出日志中的令牌、环境变量或其他密钥。
```

### 3.3 Agent 的标准输出格式

建议要求 Agent 使用以下格式，方便复核：

```text
有效 TC 总数：N

| 序号 | TC ID | 工具 | 行为 | 结果 | 日志证据 |
|------|-------|------|------|------|----------|
| 1 | ... | ... | ... | 成功/失败 | renderer.log:行号 |

排除项：
- checkRunCommandStatus：共 X 条，属于同一终端 TC 的轮询。
- plan item：共 X 个，不等于 TC。
- 其他客户端辅助调用：...
```

## 4. 人工定位与复核

如果需要自己检查，可以使用以下只读命令。macOS 示例在终端中执行；Windows 示例默认在 PowerShell 中执行。

以下命令优先使用 `rg`（ripgrep）。Windows PowerShell 命令写成 `rg.exe`，以明确调用的是可执行文件；如果系统未安装 `rg`，可使用每节给出的 PowerShell 内置命令。

### 4.1 查找 Session ID 所在日志

优先搜索纯 `session_id` 或 `trace_id`。

macOS：

```bash
rg -a -l -F '<session_id>' "$HOME/Library/Application Support/Trae CN/logs"
```

Windows PowerShell（使用 `rg`）：

```powershell
$traeLogs = Join-Path $env:APPDATA 'Trae CN\logs'
rg.exe -a -l -F '<session_id>' $traeLogs
```

Windows PowerShell（未安装 `rg` 时）：

```powershell
$traeLogs = Join-Path $env:APPDATA 'Trae CN\logs'
Get-ChildItem -LiteralPath $traeLogs -Recurse -File -Filter 'renderer.log' | Select-String -SimpleMatch '<session_id>' | Select-Object -ExpandProperty Path -Unique
```

`rg` 的 `-a` 很重要，因为部分日志或缓存可能被工具识别成二进制文件。PowerShell 内置回退只搜索 `renderer.log`；如果目标字段也可能存在于其他日志中，可去掉 `-Filter 'renderer.log'`，但搜索会更慢。

### 4.2 查看会话元数据和完成状态

macOS：

```bash
rg -a -n -F '<session_id>' '<命中的 renderer.log>' \
  | rg 'MetadataHandler|Stream started|DoneHandler|toolCallId|serverCallId|operationId'
```

Windows PowerShell（使用 `rg`）：

```powershell
$log = 'C:\完整路径\renderer.log'
rg.exe -a -n -F '<session_id>' $log | rg.exe 'MetadataHandler|Stream started|DoneHandler|toolCallId|serverCallId|operationId'
```

Windows PowerShell（未安装 `rg` 时）：

```powershell
$log = 'C:\完整路径\renderer.log'
Select-String -LiteralPath $log -SimpleMatch '<session_id>' | Where-Object { $_.Line -match 'MetadataHandler|Stream started|DoneHandler|toolCallId|serverCallId|operationId' } | Format-Table LineNumber, Line -Wrap
```

先确认：

- `trace_id` 与待查 Session ID 一致。
- 用户消息内容和时间一致。
- 会话最终状态是 `completed`。

### 4.3 查找明确的 TC 标识

macOS：

```bash
rg -a -n 'toolCallId|serverCallId|operationId|tool_call_key' '<命中的 renderer.log>' \
  | rg '<session_id>|<user_message_id>'
```

Windows PowerShell（使用 `rg`）：

```powershell
$log = 'C:\完整路径\renderer.log'
rg.exe -a -n 'toolCallId|serverCallId|operationId|tool_call_key' $log | rg.exe '<session_id>|<user_message_id>'
```

Windows PowerShell（未安装 `rg` 时）：

```powershell
$log = 'C:\完整路径\renderer.log'
Select-String -LiteralPath $log -Pattern 'toolCallId|serverCallId|operationId|tool_call_key' | Where-Object { $_.Line -match '<session_id>|<user_message_id>' } | Format-Table LineNumber, Line -Wrap
```

对找到的 ID 去重，再查看每个 ID 的上下文。

macOS：

```bash
rg -a -n -C 3 -F '<TC ID>' '<命中的 renderer.log>'
```

Windows PowerShell（使用 `rg`）：

```powershell
rg.exe -a -n -C 3 -F '<TC ID>' $log
```

Windows PowerShell（未安装 `rg` 时）：

```powershell
Select-String -LiteralPath $log -SimpleMatch '<TC ID>' -Context 3,3
```

### 4.4 检查底层 tooling 命令，但不要直接相加

macOS：

```bash
rg -a '\[tooling\].*\[message:<user_message_id>\].* start' '<命中的 renderer.log>'
```

Windows PowerShell（使用 `rg`）：

```powershell
rg.exe -a '\[tooling\].*\[message:<user_message_id>\].* start' $log
```

Windows PowerShell（未安装 `rg` 时）：

```powershell
Select-String -LiteralPath $log -Pattern '\[tooling\].*\[message:<user_message_id>\].* start'
```

这一步用于理解某个 TC 展开成了哪些客户端动作。输出行数不是有效 TC 次数，必须按服务端 TC 标识和实际语义合并。

### 4.5 Windows 使用注意事项

- PowerShell 使用 `$env:APPDATA`，CMD 和资源管理器使用 `%APPDATA%`。两种写法不能在命令行中混用。
- 路径含空格时，优先保存到变量后传给命令；手写路径时应使用引号或 PowerShell 的 `-LiteralPath`。
- 不需要以管理员身份运行这些检查。当前用户自己的 AppData 通常可直接读取。
- `Select-String` 的结果对象包含 `Path`、`LineNumber` 和 `Line`，可用于记录完整路径、行号和证据文本。
- `rg` 返回退出码 1 通常表示没有匹配项，不等于日志损坏；退出码 2 才通常表示参数、路径或读取错误。
- 日志较大时，PowerShell 内置回退可能明显慢于 `rg`。优先限定到 `renderer.log`，不要把整个用户目录作为搜索范围。

## 5. 已验证示例

某次“创建并测试 Python 定时器”的会话包含：

- 1 次写文件 TC：创建并写入 `timer_demo.py`。
- 1 次终端 TC：执行 `uv run python timer_demo.py`。
- 多次 `checkRunCommandStatus`：均为终端 TC 的状态轮询。
- 多个 `plan item`：包含计划、确认和最终回复。
- 多次自动 `readFile`：用于上下文收集，没有独立服务端 TC 标识。

因此该示例的有效 TC 是 **2 次**，而不是 plan item 数量、底层 tooling 日志行数或状态轮询次数。

## 6. 常见误区

### 误区一：把 plan item 数量当成 TC 数量

plan item 是 Agent 输出结构，不是工具调用计数器。必须继续寻找工具 ID 和执行结果。

### 误区二：把每条 tooling start 都算一次

一个 TC 可以展开为创建文件、应用补丁、刷新文档、获取诊断等多个客户端动作。

### 误区三：把命令轮询算成多次终端调用

大量 `checkRunCommandStatus` 通常只对应一个 `runCommandInTerminal`。

### 误区四：只按命令名称去重

同一会话可能真实执行两次相同命令。应该优先按 `toolCallId` 或 `serverCallId` 去重，而不是只按工具名或命令文本去重。

### 误区五：忽略失败、取消和未执行操作

如果统计目标是“有效 TC”，仅展示但未确认、被取消、没有进入执行阶段或没有产生有效结果的操作不应计入。

## 7. 日志保留与安全

Trae 日志不是永久存档。Trae 重启、升级、日志轮转、缓存清理或重置应用数据后，旧日志可能被删除。

需要留档时，建议保存：

- 完整 Session ID。
- TC 统计表。
- 关键日志行及原始日志路径。
- 统计时间和使用的口径版本。

不要直接分享完整 `renderer.log`。日志可能包含：

- 访问令牌或环境变量。
- 本机用户名和项目绝对路径。
- 命令输出和代码内容。
- 账号及会话标识。

对外提供证据前，应只截取必要行并脱敏。

## 8. 最终检查清单

- [ ] 使用了与当前操作系统匹配的 Trae 日志目录。
- [ ] 搜索了整个 Trae `logs` 目录，而不是单个 `window` 目录。
- [ ] 确认了正确的 `trace_id`、`session_id` 和用户消息。
- [ ] 找到了会话完成状态。
- [ ] 按唯一 TC 标识去重。
- [ ] 合并了同一 TC 的客户端执行阶段。
- [ ] 排除了状态轮询、配置读取和诊断刷新。
- [ ] 没有把 plan item 或 TS 数量当成 TC 数量。
- [ ] 每个有效 TC 都有行为、结果和日志行号证据。
- [ ] 输出内容没有泄露令牌或敏感环境变量。
