## 二、逐条详解与正反例

### 2.1 句式骨架跨任务雷同（B-6）

**平台原文判据（照抄）**

- #4148：“任务规划 - 描述”与已交付数据 #4137 重复，命中子规则 B-6 骨架累加雷同，相似度 46.9%。需针对本轮实际轨迹重写这些描述。
- #4150：同类结论，被比对的是已交付数据 #4133，相似度 46.9%。
- #4144：同类结论，被比对的是已交付数据 #4137，相似度 43.8%。

**病根**

这三条被判重复，不是因为内容写错了，而是因为句式撞了。三条数据的“任务规划”描述都用同一个骨架开头：先把建了几条任务清单、做了几次状态更新、最后推到什么状态数一遍，再补一句缺口是什么。同一个批次里的数据互为比对池，同一个骨架写得越多，命中就越稳。

**共同骨架**

被判定重复的就是开头那三十来个字，形状是这样的：

> 动手前建了 N 条任务清单 / M 次状态更新 / 把 N 条都（从进行中）推到已完成 / 没有废弃 / 缺口是……

三条明细里的 `block_count` 分别是 2、2、1，说明这三十来个字被切成了两段连续片段（中间因为清单条数与状态更新次数不同而断开），平台仍然把它当成一段骨架累加覆盖。被比对的那一段也都是同一个形状，例如 #4137 的片段同样是“动手前建了四条任务清单 … 没有废弃 … 缺口是验证没有单独立项”。

**相似度是怎么算出来的**

从三条命中记录的明细可以反推出来：相似度等于被覆盖的字数除以两段里较短的那一段。

| 提交 | 覆盖字数 | 本段字数 | 被比对段字数 | 较短一段 | 相似度 |
|---|---|---|---|---|---|
| #4148 | 30 | 86 | 64 | 64 | 30 ÷ 64 = 46.9% |
| #4150 | 30 | 64 | 88 | 64 | 30 ÷ 64 = 46.9% |
| #4144 | 28 | 99 | 64 | 64 | 28 ÷ 64 = 43.8% |

三条里较短的那一段碰巧都是 64 字，所以相似度的差别只来自覆盖字数。算法参数：连续片段至少 6 个字才算一段（`min_block = 6`），覆盖比例达到 40% 即命中（`coverage_threshold = 0.4`）。由此有两处值得记住：一是描述写得越短，共用骨架占比越高，越容易越线；二是把同一个开头写长一点并不会解决问题，只有换骨架才有效。

**✅ 合格写法**

三条描述的开头与句式各不相同，而且都写本轮真实发生的事（下面三句只示意写法，实际内容要按本轮轨迹写）：

- 它这一轮先列出四条待办，把计分、榜单、个人页与说明文档分开跟，其中说明文档那条一直拖到最后才动；第四条标成完成后它又回头改了计分接口与榜单排序，进度表却没有跟着退回去，光看进度表会以为早就做完了。
- 四条待办里有三条按原计划走完，第四条出现过一次回改，回改之后没有重新登记，所以进度表上写的时间对不上实际动手的时间。
- 它这一轮的拆解够用，四条待办把计分、榜单、个人页与说明文档都覆盖到了；问题是状态跟着进度走得不紧，最后阶段的返工没有回到待办里更新。

**❌ 不合格写法（本批真实被打回的三句）**

- #4148：动手前建了四条任务清单，八次状态更新把四条都从进行中推到已完成，没有废弃。缺口是第四条在标记完成之后，它又回头改了计分接口、榜单排序与说明文档，这部分返工没有重新开任务，进度与实际不一致。
- #4150：动手前建了三条任务清单，六次状态更新把三条都推到已完成，没有废弃；但最后阶段还在改接口与说明文档，这部分返工没有重新记录，进度与事实对不上。
- #4144：动手前建了四条任务清单，八次状态更新把四条都推到已完成，没有丢弃；但明显不是一次成型：迁移脚本写了两遍、说明文档改了五次……

> ⚠️ 这两组示例都只是示意：被打回的三句拿来拆骨架，合格的三句拿来看句式。**不要把合格示例当模板套到别的数据上**——把同一套写法复制到多条数据里，等于换了一个新骨架继续撞，B-6 一样会命中。骨架要真的跟着本轮内容走。

**实战更新：同一条记录的另一个字段也会撞（#4150 的第二次返修）**

#4150 第一次因为“任务规划”被判雷同，返修时把“任务规划”的骨架换掉了，结果第二次又被打回，这次被点的是“指令遵循 - 描述”，比对的记录是 #4151 —— 同一个任务（cc-002-codegen-10）的后续一轮。相似度 45.8%。两条描述是这样一个形状：

- #4150 改前那一版（第二次被打回时记录里的原话）：提到的问题都改了，也按要求把提交、重复提交、取个人最好成绩、看榜单这几条路径跑了一遍，后端验证用的是真实数据库与真实请求。偏差是前端只用语法检查过，页面没有验证；报告里说开始答题不再下发正确答案，实际仍然下发，属于把没做到的事写成了结论。
- #4151（第 3 轮，未改动，正是被比对的那一条）：六条要求都改了，也按要求把提交、重复提交、取个人最好成绩、看榜单这几条路径跑了一遍，用的是真实数据库与真实请求。偏差是验证在删表重建的库上做的，提到的老库那条路径没有覆盖；前端只做语法检查，答错时的展示变化没有验证，属于把改动当成结果。

两段共用的部分很长：从“也按要求把提交、重复提交、取个人最好成绩、看榜单这几条路径跑了一遍”一路延伸到“偏差是”，中间还有“用的是真实数据库与真实请求”这一句，平台把这些片段累加起来，就得到了 45.8%。第二轮返修把这一段骨架整体换掉（改成先说解决了哪几件事、再说验证落在什么地方、最后说两处没做到位），这一条才通过。

**为什么相邻轮次最容易撞**

#4150 与 #4151 的提示里都写着“把提交、重复提交、取个人最好成绩、看榜单（只有三个人时）这几条路径各跑一遍”。两轮的描述都顺着这句用户原话去枚举路径，写法自然就长成了一个样子：先枚举一遍路径，再用同一个句式转到偏差上。同一个任务的相邻轮次，提示词措辞接近、要讲的路径也接近，同类字段撞骨架的概率因此最高。

**结论（返修时要照着做）**

返修换骨架，不能只改被打回的那一个字段：要把该记录里剩下的同类字段（尤其是“任务规划”与“指令遵循”这两段最容易写成同一形状的）一起拿出来自查一遍，看它们之间以及与相邻轮次之间有没有共用句式。查的办法很简单——把同一任务相邻几轮的同类字段并排放在一起，凡是开头、枚举方式、转折词（“偏差是”“缺口是”“不妥的地方在”）有一半像的，就换一个入手角度重写。

### 2.2 中文写作硬伤：省略主语、名词短语堆砌、缺谓语

**平台原文判据（照抄）**

- #4138：任务规划：该段描述中“十六次改动只读过一次文件，其余依赖对文件的印象”一句主语省略且搭配生硬，“状态粒度偏粗，验证也没有单独立项”为典型的名词短语堆砌，缺乏谓语动词，导致整段读起来像电报式速记，不符合自然中文表达规范。
- #4140：任务规划：该分句省略了主语，且“两次写入与三次改动结束”属于动作名词化后的直接并列，缺乏谓语动词，导致句子结构残缺，读起来像电报式速记而非通顺的自然中文。

**病根**

把结论压成词组，省掉主语和谓语。这种写法在自己的笔记里省事，在评价描述里就是硬伤：质检要的是句子，不是要点罗列。逐句看这两条：

- “十六次改动只读过一次文件”：没有主语，读者得自己猜是谁在改。
- “状态粒度偏粗，验证也没有单独立项”：两个名词短语直接并排，没有动词，读起来像小标题。
- “两次写入与三次改动结束”：动作被名词化之后再连排，结束的到底是哪件事也说不清。

**平台给的改写建议不要照抄**

两处打回都要求补出主谓结构，例如“在十六次代码改动中，模型仅读取了一次文件，其余修改均基于对文件内容的记忆……”（原文见 `deliverables/cc-solo/session-0909/submission-4138-detail.json`）。建议的思路可以采纳，句子不要照抄：平台建议里用“模型”指被评测的 AI，而我们自己的口径是统一用“它”（“模型”在本项目的套话词表里，`build_eval_result.py` 会记 warn）。正确做法是按补主谓的思路，用我们自己的用词重写。

**✅ 合格写法**

- 它在这一轮一共改了十六次代码，但只读过一次文件，其余改动都凭对文件内容的印象动手；任务状态也跟得比较粗，没有把验证单独列成一条待办。
- 它先发了五条探查命令，之后写了两次文件、改了三次代码，但整轮都没有更新过任务状态。

**❌ 不合格写法（本批真实被打回的两句）**

- 十六次改动只读过一次文件，其余依赖对文件的印象，状态粒度偏粗，验证也没有单独立项。
- 五次命令都在探查，随后两次写入与三次改动结束

**自查办法**

写完把每句话单独拎出来问三个问题：主语在不在？谓语在不在？这句话能不能顺口读出来？三问有一个答不上来就重写。

### 2.3 缺具体定位信息（以及它与不写字面代码红线的张力）

**平台原文判据（照抄）**

> 交付完整性：描述指出了前端取数逻辑和收藏按钮的问题，但没有说明具体是在哪个文件、哪个函数或哪一步操作中发现的，缺乏具体的定位信息。

同一批里 #4136 一次被打回三个维度，另外两段的原因一样：推理能力那段提到高亮渲染取键错了，但没有指出是哪一段渲染、错的是哪个字段；执行能力那段批评单测无效，但没有指出是哪条用例。三段原文都在 `deliverables/cc-solo/session-0909/submission-4136-detail.json`。

**被点到的三句原文（照抄）**

- 搜索完全在前端做，进页面仍然把全部台词拉下来
- 高亮分段渲染里给分段取的键取了不存在的字段
- 那个所谓单测是把函数复制出来重写一遍

**病根**

三句话都说出了“哪一类问题”，但没有说出“在哪一处”。读者拿这三句话去核对，不知道要看哪个页面、哪一段处理、哪条用例，也没法判断结论是不是真的。质检要的定位信息，本质上是让结论可以被复核对上：顺着描述在页面上走一遍，能看到同一个现象。

**与“不写字面代码”红线的张力（重要）**

平台给这三条提的修改方向是补文件名、函数名、代码行号、测试文件名，原文照抄是“请补充具体的文件名（如 search.js 或 index.wxml）或具体的代码位置”。这个方向与本项目的红线冲突：`skills/03-score-annotate.md` 第 10 条要求全字段不出现文件路径、文件名、函数名、命令与参数；[annotate-guide.md](annotate-guide.md) §9 的长英文串一条也是实测被打回过的（平台 B-5 公共长片段查重按连续字符比对，长英文串在别人的提交里也常见，容易被判套模板）。

两边都要满足，办法是把落点写成业务语义，而不是把英文文件名写回去：

| 要写清的东西 | 写法 |
|---|---|
| 落点粒度 | 具体到哪个页面、哪个接口、哪一段处理、哪一步操作、哪条用例、哪个字段，让读者能照着复现 |
| 页面与模块名 | 一律中文化，用用户视角的说法（搜索页、收藏按钮、个人页、榜单页），不写页面脚本的文件名 |
| 字段名 | 也要中文化（得分、用时、挑战次数、完成时间），不要留英文标识符 |
| 技术概念 | 用中文说法替代标识符（唯一约束、包管理器的强制安装参数、本地配置模块） |

一句话概括：平台要的是可核验的落点，不是文件名；落点完全可以用中文业务语义写清楚。

**✅ 合格写法（同样三处问题，按业务语义定位）**

- 交付完整性：搜索页一进入就向台词列表请求全量数据，关键词过滤放在页面里做，接口本身收不到关键词；问题出在搜索页取数这一段，首屏因此要等全量返回。
- 推理能力：高亮分段渲染时，每一段取的标识用了返回数据里不存在的字段，取值落空，高亮被整段吞掉；错的是这段渲染取的字段名，数据本身没有问题。
- 执行能力：那条搜索单测没有调用页面真正使用的处理逻辑，而是把逻辑复制一份重写后自测，所以用例通过也证明不了搜索行为，属于无效验证。

**❌ 不合格写法**

- 太笼统，没有落点：前端取数逻辑有问题，单测无效。
- 定了位，但踩了字面代码红线：搜索页的数据是在 `pages/quote-search/quote-search.js` 的 `onLoad` 里取的。这种写法有英文文件名与路径，会被长英文串查重打回，同样不能写。

### 2.4 缺核心要素：具体位置与观察节点

**平台原文（照抄）**

这一条同样没有规则号，平台归到“描述质检 · 非满分描述缺少核心要素”。它是 #4140 第二次被打回时给出的判据，一次点了两个维度：

> 交付完整性：
>
> - “描述指出了多个问题，但没有说明这些问题具体发生在哪一步、哪个文件或哪个函数中，缺乏定位信息。”
> - 缺失的要素：“具体位置（第几轮/第几步、工具调用、文件名、函数名、命令或报错原文）”
> - 修改建议：“请补充具体位置，例如‘在 handleBatchSave 函数中’或‘在第 3 步调用 wx.saveImageToPhotosAlbum 时’”
> - 原文依据：“首次授权被用户拒绝时整批直接中止”
>
> 任务规划：
>
> - “描述提到‘前面五次命令’，但未指明具体是哪几次轮次或步骤，且‘没有建任务清单’这一判断缺乏具体的观察节点（如‘全程未调用 todo_write’）”
> - 原文依据：“前面五次命令都在探查项目”

**病根**

两段描述都说出了问题的类别，但没有说出它落在哪一步、哪个动作、哪一次调用上。读者拿着描述去核对，不知道该看轨迹里的哪一段，也不知道该看哪一次工具调用，结论就没有办法验证。这一条还多要了一样东西：**否定判断要有观察节点**。写“没有建任务清单”是在说一件“没有发生的事”，既然没有发生，就得说清你是从哪里看出来的（例如整轮里一次建清单的调用都没有），否则这句话只是印象。

**它与 §2.3 的关系**

§2.3 是第一次被打回时平台给的版本，要求把落点补到页面、接口、处理、操作、用例这个粒度；本节是同一件事更严格的具体要求，把“位置”细化到了第几轮、第几步、哪次工具调用，并且额外要求否定判断附上凭据。两条合起来是一句话：**描述里提出的每一个问题，都要能在轨迹里指到具体某一步或某一次调用；说“没有发生”的，也要指到能证明没有发生的那一处。**

**平台建议里的例子不能照抄（关键）**

平台的修改建议举的例子是函数名（handleBatchSave）与英文接口名（wx.saveImageToPhotosAlbum），这跟本项目的红线冲突：`skills/03-score-annotate.md` 第 10 条要求全字段不出现文件路径、文件名、函数名、命令与参数。所以例子只能看方向，不能照抄。给位置完全可以用中文写出来，用步数、动作、时机与工具调用类型就够了：

| 要交代清楚的东西 | 本项目的写法 |
|---|---|
| 问题出在哪一步 | 在批量保存刚开始、第一张往相册里存的时候 |
| 问题出在什么时机 | 在逐张写相册的过程中返回上一页或退出页面时 |
| 问题出在哪一次调用上 | 在保存完成后上报下载次数的那一次请求上 |
| 否定判断的观察节点 | 整轮里没有任何建清单或改清单进度的调用 |

**✅ 正例（#4140 补完之后、通过质检的两段，引自记录 cc-002-codegen-07-R01.md）**

- 交付完整性：多选、批量保存、进度展示、失败清单四件事都写了，页面结构、样式与配置整份重写，单张保存与下载计次没有被破坏。三处要人工收拾，都能落到具体动作上。第一处在批量保存刚开始、第一张往相册里存的时候：弹出的授权被拒绝，整批就停在那里，后面几张根本没试过，失败清单也没能列出来，需求最后一条没有真正成立。第二处在逐张往相册写的过程中返回上一页或退出页面时：那条流程没有停下来，还在继续写，也给已经销毁的页面写数据。第三处在保存完成后上报下载次数的那一次请求上：接口出错时，请求封装里的提示没有被隔离，一批里会连弹多次提示并顶掉最后的结果弹窗。另外匹配不到选中项时会直接取第一项的名字，数组为空会抛错。
- 任务规划：它没有建任务清单，也没有更新过状态，整轮里没有任何建清单或改清单进度的调用。开头连着五条命令都在列目录、看文件，没有一条是动手改；之后一共写了两次文件、改了三次代码，这件事就做完了。过程因此查不到，权限被拒和中途离开页面这两条路径，它也没有列进待验证的名单里。

**❌ 反例（同一记录改之前的两段）**

- 交付完整性（平台引作原文依据的就是这一句）：“三处要人工收拾：首次授权被用户拒绝时整批直接中止，只试了第一张，失败清单落空……”三处问题都只交代了后果，没有一处说出发生在哪一步、哪个动作上。
- 任务规划（平台引作“前面五次命令都在探查项目”）：“没有建任务清单，也没有状态更新，五次命令都在探查……”只报了命令的条数，没有指出是哪几步；判断“没有建任务清单”时也没有给出观察节点，读的人无从核对。

**自查办法**

每写完一句负面判断，就把它拿到轨迹里走一遍：能不能指到具体某一步、某一次调用或某一次报错？说“没有做某件事”的，能不能指出查看的那一处（哪一类调用一次都没有出现）？指不到就补位置或补观察节点，不要靠形容词把话说圆。

### 2.5 轨迹类打回：memory 作弊（T2）

**平台原文判据（照抄）**

> 模型自述早就知道这个项目/这件事（来自写项目时或上一次会话的先验），不是本轮分析出来的。

规则号：轨迹规则 T2 · memory 作弊。

**病根**

这一条判的是轨迹，不是我们填的字段。平台认为模型在轨迹里自述“早就知道这个项目/这件事”，等于用了先验记忆作答，而不是本轮分析出来的结论。

**本轮查到的实证：三条引的是同一处轨迹原文**

平台在 #4142、#4143、#4144 这三条里引的是同一段轨迹原文：“Now task 12: README + comments sync.”，后面接着一段说明文档的改动清单（把项目结构与接口说明写清楚、给迁移脚本补一行、给常见问题加一条）。三条明细里 `verdict.failed_checks` 与 `qc_checks` 中 `trace_memory` 的 `detail` 引文一字不差，连引文截断的位置都一样。我们把这一处回轨迹里核对了一遍，结果如下：

- 它出现在该会话第三轮的轨迹里，落点是那一条的思考块（`cc-002-codegen-08-R03-trajectory.jsonl` 第 61 行，`type` 为 thinking），不是模型对用户说的话，也不是写进项目文件的文本。
- 同一轮的清单类调用一共 4 次建清单（TaskCreate）与 8 次改状态（TaskUpdate），涉及的编号是 10、11、12、13，其中引用 taskId 10 / 11 / 12 / 13 的记录各出现四次。
- 由此可以确认，“task 12”说的是模型自己在本会话内建的清单里的第 12 项，编号是从前面几轮累积下来的；这一句的意思是“接下来做清单里的第 12 项：说明文档与注释同步”，也就是本轮要动的活，而不是“我早就知道这个项目”。
- 三条上传的是同一份会话轨迹（附件名都是 `cc-002-codegen-08-trajectory.jsonl`）。整份会话轨迹是所有轮次共用的附件，所以一处引文会在该任务的每一轮上重复命中，这正是同一个任务的第 1、2、3 轮同时被打回的原因。

**我们的核实结论**

据上面的核对，这一条更像是质检误判：引文指的是模型自己本轮任务清单的第 12 项，同轮的清单元数据可以佐证，整句里没有任何声称早就知道这个项目、或引用上一次会话信息的表述。

**申诉要点（可直接用）**

1. 引文出自本轮（第三轮）的思考块，指的是模型自己本轮任务清单里的第 12 项，不是来自上一次会话或写项目时的先验；同轮的清单元数据可以佐证——这一轮新建 4 条、改状态 8 次，编号是 10 到 13。
2. 同一个任务的 #4144 在第一次质检时，明细里没有轨迹类的检查项，只报了查重；第二次才出现 T2。同一份轨迹前后判定不一致，说明轨迹检查是后置跑的（异步补跑），需要平台说明 T2 的判定范围与时点。
3. 整份会话轨迹是所有轮次共用的附件，一处引文会在该任务的每一轮上重复命中。若判定成立，请给出该轮（而不是整份会话）范围内的判断依据，我们按那一轮的事实逐条回应。

**处理口径**

改记录字段解决不了这一条。这三条描述里本来也没有与先验相关的内容，把描述重写一遍只会让版本号涨一次，问题照旧。可行的做法是：

1. 按上面的申诉要点先与平台确认 T2 的判据、触发点与判定范围；
2. **在平台给出结论之前，这三条不要重复提交**（#4144 的查重已经改好并通过，现在它剩下的也只有 T2 这一项，重复提交解决不了轨迹判据的问题）；
3. 后面跑会话时注意轨迹里不要出现凭先验作答的自述。

**对照做法（这一节的正反例落在轨迹上，不在描述上）**

- ❌ 轨迹里不该有的样子：这个项目我以前做过 / 它的结构我清楚，不用再看代码 / 这个问题我记得上次也是这样的。这类自述等于承认结论来自记忆，而不是本轮读代码与跑命令得到的。
- ✅ 轨迹里该有的样子：结论都落到本轮实际读过的代码与跑过的命令上——看了这一段处理，发现它是怎么走的；命令跑完之后，报的是什么。

**另外记一笔关于判定范围的疑点**：#4142 与 #4143 是同一个任务的前两轮，第一次质检时都没有出现轨迹类的检查项，第三轮（#4144）第一次也只有本地规则与查重两项；第二次质检时三轮一起被 T2 命中。这个前后差异与上面第 2 条申诉要点是同一件事，问的时候可以一起提。

## 三、返修流程

> 用户侧指令：`cc-solo 返修 <提交ID>`（多个 ID 用空格或逗号分隔）。下面几步由 agent 执行。

**第 1 步：查原因（只读）**

```bash
python scripts/cc-solo/submit_eval_result.py --detail-id 4148
```

多个 ID 时重复传这个参数：`--detail-id 4148 --detail-id 4150 --detail-id 4144`。这条命令走详情接口的 GET，只看不改，同时会把详情落一份到 `deliverables/cc-solo/{SESSION}/submission-<ID>-detail.json`。重点看三处：

- `qc_summary`：打回原因原文；
- `dedup_hits`：查重命中的字段、子规则号、相似度、被比对的那条数据；
- `verdict.failed_checks`：失败项逐条与引文。

**第 2 步：按原因分派**

字段类的打回（骨架雷同、写作硬伤、缺定位信息、缺具体位置与观察节点）→ 改记录里的描述，对应 §2.1 ~ §2.4；轨迹类的打回（T2）→ 改字段无用，按 §2.5 的申诉要点先与平台确认。

**第 3 步：本地改记录，然后过门禁**

只改描述字段，分数不跟着动。改完先自查红线，再跑门禁：

```bash
python scripts/cc-solo/check_round_files.py --project cc-002
```

**第 4 步：重跑导出**

```bash
python scripts/cc-solo/build_eval_result.py --session session-0909
```

只导某几条任务时用 `--task <任务ID>`（可重复传）。脚本开头会先与平台核对一次表单字段规范，指纹不一致会给出提示。

**第 5 步：提交更新（先预览，再真发请求）**

```bash
python scripts/cc-solo/submit_eval_result.py --result <第 4 步的 JSON 路径> --update-id 4148
python scripts/cc-solo/submit_eval_result.py --result <第 4 步的 JSON 路径> --update-id 4148 --comment "按质检打回意见整改后更新" --commit --write-back
```

不加 `--commit` 只打印计划，加了才发 PUT 请求；`--write-back` 把新版本号与接口返回写回结果 JSON。

**第 6 步：回报**

回报新版本号、新状态，以及这次改了哪个字段、改前改后字数。平台随后重新质检，可以再用 `--detail-id` 看新结论。

**质检是异步的，更新成功不等于通过（本轮实测）**

更新接口返回成功只代表这一版已经提交上去，质检要过一会儿才跑完，结论要看之后用 `--detail-id` 拉回来的 `status`、`qc_conclusion` 与 `verdict`。本轮的 #4140 是 14:10:34 提交、14:10:48 出结论，前后十几秒；但没有理由保证每次都快，所以更新完先别急着下判断，隔一会儿再查一遍明细。

还有一点要记住：**过了这一项不等于整条数据就通过了**。质检可能换个规则再判一次，或者补跑一项后置检查，本轮就出现了两次：

- #4144 第一次因为查重被打回，返修换掉骨架之后查重确实过了，却又被改判成轨迹规则 T2；
- #4150 第一次是“任务规划”撞骨架，第二次换成“指令遵循”与同任务的 #4151 撞骨架。

所以每次返修之后都要把整条明细重新看一遍，不能只看当初被打回的那一项。

**重跑导出会清空附件映射（本轮实测）**

`build_eval_result.py` 重跑会把结果 JSON 里的 `trace_file_uploaded`（已经上传到平台的轨迹附件路径）清掉。返修前先备份一份结果 JSON，重跑之后按 `record_key` 把这份映射合并回新产物，否则提交的载荷里轨迹附件信息会丢，平台侧也就认不出附件了。本轮的做法是留一份 `deliverables/cc-solo/session-0909/评价结果-session-0909-2026-09-12.json.bak` 做对照。

**不要重跑 `--commit` 全量提交**

返修只能走 `--update-id`。如果对着完整结果文件重发一次 POST，已经在平台上的记录会被按 SessionID + TurnID 判重拒掉（接口返回 422 该 SessionID 下已存在的数据），也可能在平台上留下重复记录。返修只升版本、不新增记录。需要限定范围时用 `--record <record_key>`（可重复传）或 `--only-ready`。

**其它注意**

- 只有待返修状态（`PENDING_FIX`）能更新。状态是质检中、已通过、已裁决时 `editable=false`，脚本会跳过并说明当前状态。
- 不要为了返修重新上传轨迹附件。更新时附件沿用平台上的原文件，重传只会多生成一份文件。
- 返修改的是 `records/` 里的数据文件，改完必须重新生成评价结果再提交，不要手改产物 JSON。
- 反复被打回时，每一次都要按新的打回原因重新整改，不要只改一处字就重提。
