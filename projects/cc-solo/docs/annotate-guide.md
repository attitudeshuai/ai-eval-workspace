# 标注速查（annotate-guide）

> 由 `docs/ClaudeCcode 用户满意度标注.docx`（0926 期）提炼，供人工评分/质检快速查阅。
> ⚠️ 本清单可辅助 AI 起草「找问题/写原因」。AI 起草的分数与依据文本，落盘/投递前须先经 humanizer-zh 去 AI 化（练习阶段无需人工确认；正式交付再人工复核），且严格按五维模式、依据含可核验证据、避免套模板与雷同。

## 1. 交付表头（提交表单字段）

**提交与题目信息**：`任务类型`、`任务难度`、`语言/框架`

**运行环境（同一会话各轮填同一组值）**：`Harness`、`Harness版本`、`操作系统`、`环境可复现等级`、`初始环境快照`

**会话与轨迹定位**：`User Prompt`、`SessionID`、`TurnID/PromptID`、`轨迹文件`
> `轨迹文件`：Claude Code（容器做，题号 = 任务 ID）→ `records/{任务}/{任务}-trajectory.jsonl`（来自容器导出；容器入口见 runbook.md / runbook-windows.md）。

**五维打分与依据描述**：`交付完整性`(1-5)+`交付完整性-描述`、`指令遵循`+`指令遵循-描述`、`任务规划`+`任务规划-描述`、`推理能力`+`推理能力-描述`、`执行能力`+`执行能力-描述`、`其他问题`

> TPM 内部可自行增列（如 Repo URL、截图附件、备注），但不得删减上述字段。

## 2. 任务类型（按本轮对话主要意图，一轮单选一个）

| 类型 | 口径 |
|------|------|
| 0-1 代码生成 | 基于 PRD 或自然语言描述的新项目/完整模块构建 |
| Feature 迭代 | 在已有功能基础上的平滑扩展 |
| Bug 修复 | 逻辑修复、报错排查、安全漏洞修补 |
| 代码理解 | 解释逻辑、寻找潜在风险、回答技术细节 |
| 代码重构 | 性能优化、可读性提升、解耦 |
| 工程化 | 环境配置、依赖管理、CI/CD 相关 |
| 代码测试 | 单测、集成测试等 |

**按天维度分布偏序**：`0-1代码生成 / Feature迭代 / Bug修复` > `代码理解 ≈ 代码重构` > `其他`

### 2.1 类型自查：别把「在既有代码上加功能」标成 0-1代码生成（2026-09-13 实测一次被打回 12 条）

本批 29 条待返修里，管理员判了 **12 条「整体 · 任务类型与 Prompt 意图错配」**，全部是**第 1 轮标成 `0-1代码生成`、实际却是在既有项目上做改造**。平台的判据很固定：`0-1代码生成` = 「从零生成一个新项目」，只要 Prompt 交代了**已有的表 / 页面 / 接口 / 中间件**，本轮就是 `Feature迭代`。

**判定只看 Prompt 里有没有「既有前提」**，不看任务名（`cc-002-codegen-xx` 只表示它是第 1 轮，不代表类型）：

| Prompt 的写法 | 类型 |
|---|---|
| 描述要**新建**的独立模块 / 完整工程，无任何既有前提 | 0-1代码生成 |
| 「X 现在只能……」「X 已经写死在 Y 里」「X 表 / 页面 / 接口已存在」，然后要加功能、改逻辑、改口径 | **Feature迭代** |
| 「点了报错 / 崩了 / 数据对不上」，以修复既有缺陷为主 | Bug修复 |
| 加 CI、改部署、加定时脚本、换依赖配置一类 | 工程化 |

**从本批实测抄下来的 13 个反例**（全被要求改成 Feature迭代）：给壁纸页加多选批量保存、给发帖页加草稿、给评论加父评论字段、把写死的每日台词改成按日期取、把敏感词从中间件挪到数据库、给猜剧情加榜单、给剧集详情页加高光台词、给既有接口加内存缓存、给三个页面配分享卡片、改既有收藏逻辑的登录态、给台词表加音频字段与播放按钮、给首页加三步引导、给已有 news 写定时下架任务。

**两个最容易判错的边界**：

- 「表已经建好了但没人往里写数据，把发放接上」——表是既有产物，接发放逻辑属于 **Feature迭代**，不是 0-1。
- 「写一个每天跑一次的任务」——单看像新建，但若它挂在既有应用里（改 `app.js`、既有 news 路由），仍是 **Feature迭代**。

**自查口径**：出完题、录入前，把 Prompt 的第一句读一遍，问「这句话里有没有一个已经存在的东西？」，有 → `Feature迭代`；没有、整块是从零起 → 才写 `0-1代码生成`。**一轮只能选一个类型**。

## 3. 任务难度（人类视角判断）

| 难度 | 口径 |
|------|------|
| 简单 | 意图明确，沿已有模式机械修改/局部实现（多文件但模式高度一致、核心判断很少也算） |
| 中等 | 需理解局部到跨模块调用/数据流、做实现决策；有边界条件但无需重设计架构 |
| 困难 | 整合多模块/系统约束、关键设计取舍、复杂状态/兼容/权限/并发/性能/异常 |
| 地狱 | 极高决策复杂度、需求开放或约束隐蔽、架构级判断、SOTA 也大概率失败 |

**硬性**：首轮任务严禁「简单」；后续轮次因模型产物差产生的简单 bugfix 可提交。**本期口径补充（2026-09-11）：所有轮次一律不写「简单」**——后续轮次的修复题即便范围不大，也按「中等」记录，避免被审核按过于简单题处理。

**过于简单题判定（同时满足 ≥2 项 → 拒收）**：

| 维度 | 特征 |
|------|------|
| 修改范围 | 单文件局部修改、纯函数级实现（LeetCode 题、独立工具函数） |
| 上下文依赖 | 不需要任何 Repo 上下文、纯文本 Prompt 即可完成 |
| 交互轮次 | 大多数模型 1 轮即可完美交付 |
| 技术广度 | 单一文件、单一语言、不涉及前后端联调/跨服务 |

## 4. 五维评分表（每轮单独打分；1-5 整数）

| 维度 | 1 | 3 | 5 |
|------|-----|-----|-----|
| 交付完整性 | 完全失败/严重事故/极其恶劣虚假成功 | 勉强达标，明显 Bug 需人工微调，或轻微虚假成功 | 一次性完美跑通，主动补全隐性需求，零虚假成功 |
| 指令遵循 | 彻底无视/反向执行所有约束 | 遵循核心但遗漏 1-2 个显式约束 | 分毫不差，无任何自作主张 |
| 任务规划 | 无头苍蝇，无步骤/状态概念 | 有大方向规划但子任务不细致、状态明显遗漏 | 拆解清晰合理，阶段状态持续更新，歧义主动求证 |
| 推理能力 | 需求理解完全错误/严重幻觉/死循环 | 理解主要任务但遇错需多次尝试 | 一针见血定位根因一次性修复，思考量与难度匹配 |
| 执行能力 | 工具严重滥用/缺失 | 明显冗余调用但最终完成 | 调用精准最小化，一步到位，能批量/并行 |

> 每档完整锚点见 `docx` 第三步；此处为 1/3/5 关键锚点速查。每条数据的五个「-描述」均必填。

> **任务规划校准（agentic 会话要点）**：Claude Code 这类自动轮常用 `TaskCreate/TaskUpdate` 建正式计划并持续更新状态，**必须先数工具调用再下结论**（§10 第 5 条），不能凭「没看到文字计划」就写「无计划」。打分时：
> - **5**：开局用 TaskCreate 给出清晰分阶段拆解、TaskUpdate 全程持续更新（各任务 in_progress→completed）、遇歧义主动求证，返工极少；
> - **4**：有 TaskCreate/TaskUpdate（拆解+状态维护），偶有状态更新不及时、少量返工（返工须为**模型自身**问题，不能是环境故障）；
> - **3**：**无任务清单跟踪**（TaskCreate=0）、一次到位的 find→fix→verify，方向清楚但无显式状态跟踪；
> - **2**：无拆解、盲目写、无状态、靠猜。
> **必须保持一致**：同批任务按**同一尺度**打分，且**分数与描述自洽**——描述不能写「没有计划/状态记录」却给 4 分（见 §9）。

## 5. 依据描述（不满意原因）硬性要求

写之前问自己三问：*模型从哪一步开始降智的？什么具体操作很弱智？人类高级工程师会怎么做？*

硬性要求（质检会看）：

- **过程与产物都要分析**：分别说清「过程哪里差、产物哪里差」。
- **定位到具体环节**：指明哪个步骤、哪个工具调用、哪次文件改动。
- **用证据不用形容词**：引用报错信息、出错文件名/函数、漏掉的具体需求；禁止「效果不好/不行/一般」这类笼统表述。
- **只写模型能力问题**：不写环境/网络波动导致的请求失败等。
- 三要素：**触发节点(When)** + **实际行为(What)** + **业务影响(Impact)**；好的原因还要指出根因和正确做法。

合格示例（供人工对照）：

- ✅「prompt 要求支持分页，产物只实现了列表查询，完全没动分页参数，产物不完整。」
- ✅「在第 3 步用 edit_file 改 auth.py 时引入了未定义变量 token，且未运行就宣称完成，导致代码报错。」
- ✅「规划混乱：模型在第 2、4、6 步三次重复读取同一个 config.py，且第 5 步改完没运行就宣称完成，存在验证缺失。」

## 6. 过程/产物常见问题清单（找问题方向，人工自查用）

**过程类**：指令遵循（忽略约束/漏需求/擅自改技术栈）、任务规划（无规划/顺序乱/目标漂移/来回反复）、工具使用（参数错/改前不读/失败反复重试）、幻觉（编造 API/文件/函数、声称做了没做）、验证缺失（不测试就说完成、对报错视而不见）、纠错能力（死循环/重复无效修复/轻易放弃）、交互沟通（该问不问/进度误导）。

**产物类**：正确性（编译运行失败/逻辑错/边界挂/引入回归）、完整性（漏需求/半成品/留 stub TODO）、代码质量（可读性差/无错误处理/违反 repo 规范）、过度工程、偷工减料/造假（硬编码/假数据/删测试 hack/占位）、破坏性（删改无关代码）、安全（引入漏洞）、UI/美观度。

## 8. 提交与轮次约定

- 一轮 = 一次交互（用户提问 + 模型回答）；每个单轮对话一条数据、单轮验收。
- 每会话窗口 ≤ 10 轮；对话满 10 轮后无论是否完成，不继续引导，开新任务。
- 工程故障（网络/模型不稳定导致请求失败）不计轮次；**思考次数超限需人为「继续」计轮次**。
- 用户输入「继续」的轮次：prompt 可写「继续」，任务类型/难度综合上一轮原始需求判断；评价标准仍是上一轮用户希望模型完成的任务。
- 前几轮翻车但最后一轮修正：前几轮通常低分，最后一轮按本轮表现单独评（反复自纠磕绊→体感差；高效回归→可高分）。
- 多模态 prompt：除 prompt 外需另传「prompt附件」字段（本模板内部字段可承载）。
- **提示词不得有空行（红线，2026-09-13 起）**：首轮与后续轮次的提示词全文都不得出现空行，一段一行、段间只用单个换行。空行粘进容器输入框会被当成回车提前提交，题被截断且镜像不支持恢复会话；提交表里的 `User Prompt` 也会原样带上这串空行。落盘前用 `scripts/cc-solo/lint_round_prompt.py` 自查（含空行记 error），此前已发出的提示词不追改。
- 快照：填 commit permalink（`https://github.com/<org>/<repo>/commit/<40位完整SHA>`），用完整 SHA；仓库 push 到评测团队可访问远端（设为 public 公开仓库，或至少加协作者）；禁止 force-push/rebase 改写已提交快照；凭据（.env、密钥、token）不得进仓库。

## 9. 评分与描述一致性自查（质检红线，避免自相矛盾）

评分跟着描述走、描述跟着真实轨迹走，二者必须自洽；**描述不得凭模型总结/摘要臆造，更不能写反**。

下表里注明“实测被打回”的几条，都是平台真实退回过的写法；每条的原始判据、病根与正反例见 [reject-reasons.md](reject-reasons.md)。

| 检查点 | 要求 |
|--------|------|
| 任务规划 | 给 4+ 时描述必须体现「有拆解 + 有状态回报/进度/纠错」，**不能写「没有可查的计划或状态记录」**。按锚点：无拆解、几乎无状态追踪、遇歧义靠猜 → **2 分档**；有方向但子任务不细、状态明显遗漏 → 3 分档。写实话再打分，别分数与描述打架。 |
| 交付完整性 | 避免「XX 项全部实现」这类绝对表述；只要有未验证/未覆盖项，就写「主体已实现，XX 尚未验证到位（未完成验证项）」，分数与之一致（4 分档需有明确的未验证项作理由）。 |
| 具体数字 | 文件数/行数/工具调用数等要**对照真实产物**（`git diff --stat`、轨迹 `tool_use` 计数），不得凭模型总结里的估算；拿不准就写「约」。 |
| 方向一致性 | 高分（≥4）描述不得含强失败词（失败/不可用/未实现/未完成…）；低分（≤2）描述须含负面证据；避免为凑分数硬编反向证据。 |
| 真实性 | 描述里写到的功能/验证（tsc、构建、冒烟、自测）必须在轨迹/产物里有对应命令与结果；没有的不能写「通过」。 |
| 独立阅读：不跨轮次、不与改动前对比（红线） | 每条描述都要能**单独读懂**，读者不该需要先知道前面几轮或改之前是什么样。两类写法都禁止：① 跨轮次承接——「上一轮」「前一轮」「上轮」「上一版」「之前那轮」；② 与改动前对比——「比改动前」「改了之后比原来好」「原先」「原本」「此前」。想说退步或修好了，**直接陈述现象与现状**：「正确选项不再高亮」（不写「比改动前退了一步」）、「副本里多余的依赖目录已清掉」（不写「上一轮留下的依赖目录已清掉」）。机器检查在 `build_eval_result.py`：`CROSS_ROUND` + `PAST_COMPARE`，五个「-描述」命中即 **error 阻塞提交**，user_prompt／其他问题／语言框架里记 warn（人工原文不改写）。 |
| 描述骨架不得跨任务雷同（红线，实测被打回） | 同一批数据里多条“任务规划-描述”如果用同一句式开头（“动手前建了 N 条任务清单／M 次状态更新／把 N 条都推到已完成／没有废弃／缺口是……”这一套），会被平台按 **B-6 骨架累加雷同**打回，实测相似度 **43.8%~46.9%** 即判雷同（返修改写批次里实测 **47.7%** 也被判中：用「用户报的 N 条逐条能对上／改动没有越出…／偏差是…／这个取舍它自己定了没有向用户求证」这一套骨架批量改多条，会与同批已交付数据的骨架撞上）。算法是去掉标点后按连续片段比对：连续 6 字以上算一段，共用片段占两段中较短一段的 40% 以上即命中（相似度 = 被覆盖字数 ÷ 较短一段字数）。写法要围绕本轮真实内容展开，**各条描述的骨架互不相同**；把描述写长或写短都解决不了，只有换骨架才有效。写完一批描述后横着比一遍开头；**返修改写批量动手时，同一条规则的多处整改也要逐条换结构**，别指望「补齐三要素」的固定句式能过关。详见 [reject-reasons.md](reject-reasons.md) §2.1。 |
| **同一任务相邻轮次最容易撞骨架（红线，本批实测 3 处）** | 一个任务的多轮描述出自同一支笔，同一维度的骨架最容易写成一个模子。本批实测三处都落在「任务规划」：`21#R02` 与 `21#R03` 都是「它全程没有建立任务清单，也没有写下任何状态更新：第 1 次调用…第 N 次调用…」（相似度 56.6%）；`26#R02` 与 `26#R03` 都是「从第 1 次调用…开始，到第 N 次调用…结束」（48.3%）；`25#R02`／`25#R03`／`25#R04` 都是「N 条清单…M 次状态更新…推到已完成、没有废弃条目…验证也没有单独立项」。**同任务各轮的描述写完要并排看开头与结尾**（按任务分组打印各轮同一维度的首句最省事），确认骨架错开再交；整改时整段换视角——换掉「先列清单再点状态」的叙述顺序，改成从验证环节、从返工代价、或从该轮独有的证据切入。 |
| 描述必须是通顺的完整中文句（实测被打回） | 不得用名词短语堆砌、省略主语或缺谓语来压缩结论。被打回的实例：“十六次改动只读过一次文件，其余依赖对文件的印象，状态粒度偏粗，验证也没有单独立项”“五次命令都在探查，随后两次写入与三次改动结束”——前者主语省略、名词短语直接并排，后者把动作名词化之后连排、缺谓语，读起来像电报式速记。每句话都要有主语与谓语，主语可以用“它”；写完把每句单独拎出来读一遍，读不通就重写。平台打回建议里会让我们补主谓，**思路可用、句子不要照抄**：它的示例句用“模型”指被评测的 AI，照抄会把套话词带进评价结果。详见 [reject-reasons.md](reject-reasons.md) §2.2。 |
| 定位信息要写到位（实测反复被打回） | 说某处有问题时，要写清是在**哪个页面／哪一处界面／哪一段处理／哪一步操作／第几步工具调用**上发现的，以及**哪个字段**错了，并给出实测方式与数字；不能只说“前端取数逻辑有问题”“单测无效”。**文件名、方法名、路径可以直接写**（2026-09-13 起平台不再判英文重复，反倒要求落点足够具体；实测写到「第 4 步整段重写演示数据」「第 8 到第 10 步改监控页时定下的 `stale` 判断」这种粒度才过）。 |
| **次数统计必须带对象（2026-09-13 第二轮返修实测打回 7 条，全栽在这条）** | 光有次数不算位置。「四十次调用里只有一次被拒」「三次没成功」「两次试探略冗余」「多花了五次命令」这类**没有对象的次数**会被判「读者无法定位到具体位置」「无法核验」。必须把每次失误**逐条摊开**：第几次工具调用 + 文件名或函数名 + 命令原文或报错原文。正例：「第 12 次调用改 `backend/src/models/post.js` 时把计数字符串当数字传入，接口返回参数类型不合法，改动被拒后当场改正」「第 12 次调用的验证脚本只建了编号 42 的用户，却拿编号 43 的过期令牌去请求下载接口，插入下载记录时外键找不到对应用户，接口返回 500；第 13 到第 17 次调用连跑五条排查命令才把范围缩回这条用例」。同理，**指代不能空**：`查不清的那条`、`同一条现象`、`这一步`、`那处判断` 一律不写，直接点名哪一组现象、哪个页面、哪个文件、第几次调用。 |
| **环境原因不得算进「执行能力」（2026-09-13 实测打回）** | 容器或环境缺依赖（没装数据库访问组件、精简基础镜像没有编译工具链等）造成的调用失败，**不能作为「执行能力」的扣分依据**——平台原话「这不是模型自身能力造成的」。扣分依据要换成**模型自身失误**：自己写错断言或桩、命令参数写错、同一段逻辑连着换三版、自查命令过滤条件写错导致没查出问题。原描述里的环境失败可作为背景一笔带过，但**不得挂在扣分点上**。 |

| **4 分档也要写扣分点（2026-09-12 实测打回）** | 4 分描述整段只肯定、一句不足都没有，会被判「打分与描述极端背离」；4 分档同样要写清这一维具体哪里不足以及造成了什么后果（只有 5 分档才允许通篇肯定）。 |

## 10. ⚠️ 打分取证硬性原则（重点 · 反复被打回后提炼，务必遵守）

> **根本教训：打分和写描述必须「先取证、再打分」，绝不能拿模型的自述总结或主观猜测当依据。** 下面每条都是实际被打回过的点。

1. **先取证再打分（硬性）**：写任何一条分数/描述前，先到轨迹里核对真实证据——
   - `TaskCreate/TaskUpdate` 计数（计划与状态跟踪）、`tool_use` 调用数、具体执行过的命令（`npm run build`/`vite build`/`tsc`/脚本测试/浏览器验证）。
   - 涉及「功能/验证」的描述（tsc、构建、冒烟、自测等）必须在轨迹里有**对应命令与结果**才能写「通过」。
2. **环境/系统故障不计入模型能力（硬性）**：自动模式分类器超时、网络波动、依赖/JDK/lombok 版本、沙箱限制等**环境/系统问题**，**一律不得**作为「模型规划/执行低效、反复调试、状态缺失」的扣分理由，也不得写成模型能力问题；该类问题应标注「属环境/分类器问题，非模型过错」。**2026-09-13 实测打回案例**：某条「执行能力-描述」把轮次里「环境没装数据库访问依赖导致的一次调用失败」写进了扣分依据，平台判「这不是模型自身能力造成的」，要求改掉；扣分点改为该轮自己写错断言与桩之后当场改正的两次失败。
3. **满分须有对应验证（硬性）**：涉及 **UI/响应式（手机/PC 适配、无白屏、无 console 报错）** 的「交付完整性/指令遵循」满分，**必须有真实浏览器或端到端实测证据**。仅「构建通过、预览服务 200、脚本测试」**不足以证明 UI/运行时表现**；若无实测 → 不给 5，并写明「仅构建/脚本验证，缺浏览器实测」。
4. **描述 = 轨迹 = 分数，三者一致（硬性）**：描述所写即轨迹所示、分数与描述自洽。反例：描述写「无正式计划/状态表」却给 4 分（评分表 4 档要求有拆解+状态跟踪）。
5. **任务规划要先看工具调用**：agentic 会话里模型**常用 `TaskCreate/TaskUpdate` 建正式计划并持续更新**，这本身就是「拆解清晰 + 计划持续维护」→ 4 或 5 分。**不能因为「没看到文字计划」就写「无计划」**；必须数工具调用。若确有 `TaskCreate/TaskUpdate`（如 5 次 Create + 10 次 Update、各任务 in_progress→completed），则规划不应低于 4。
6. **去 AI 化必须调用 skill**：AI 起草的文本，落盘/投递前**必须先经 `skills/humanizer-zh/SKILL.md` 完整流程**（28 条规则全查：符号/AI 词/句式套路/翻译腔/长定语），**不得只手动删符号、避关键词**。

> 检验方法：写完描述后反问自己——「这句话轨迹能直接证明吗？」「满分项有对应实测证据吗？」「我有没有把环境故障算到模型头上？」如果有一项答不上来，降档并改写成可验证的事实。
