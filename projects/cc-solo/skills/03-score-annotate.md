# cc-solo 五维打分（轨迹分析 + 五维录入）

## 功能概述

对**某一轮**对话（一条数据）做五维打分与依据录入。打分依据来源二选一：**人工撰写**（原样录入）或 **AI 代打**（默认，见下「分析调用链路」）。本技能负责：

1. **读轨迹**（= solo 02-result-analysis 的「读对话内容」）：Claude Code→本机 `records/{项目}/{项目}-{类型}/{项目}-{类型}-{索引}.jsonl`（容器导出）；按 SessionID/TurnID 定位第 N 轮的 User Prompt + 模型 thinking + tool_use/tool_result + 最终回答
2. **读产物**：对照 `source-code/{项目}/{项目}-{类型}/{项目}-{类型}-{索引}/`（任务副本，本轮代码产物）的 git 变更（`git diff`/当前代码），核实模型声称的改动与真实改动
3. **路线 A**：调用 `skills/implementation-reviewer/SKILL.md` 做代码产物质量评价（6 维度）
4. **路线 B**：自行做对话过程分析（规划/推理/工具调用/虚假完成），映射到五维
5. 合成五维分数（1-5）与五条必填依据 + 不满意（过程+产物汇总）+ 其他问题
6. AI 起草内容**先经 `skills/humanizer-zh/SKILL.md` 去 AI 化**，再做机械校验（字段范围/非空/方向一致性/AI 痕迹）

> 🔴 **分析是红线**：AI 代打**必须**读轨迹文件 + **必须**调用 implementation-reviewer，二者缺一即整批拒收；不得脱离轨迹/产物凭空打分（详见 SKILL.md「质量红线」）。

## 分析调用链路（AI 代打必走；双路：路线A 产物 + 路线B 过程）

```
读轨迹 → 读产物 → 路线A(implementation-reviewer) → 路线B(过程分析) → 合成五维 → 去AI化 → 落盘
```

1. **读本轮轨迹切片**：`records/{项目}/{项目}-{类型}/{项目}-{类型}-{索引}.jsonl`（02-round-capture 已从容器导回；Claude Code 容器导出），按 `type==user` 且 content 为字符串定位本轮起点，其 `promptId` = TurnID；该轮内 assistant 的 thinking / tool_use / tool_result / 最终 text 全归属本轮。（= solo 的「读取对话内容」，cc-solo 里就是读轨迹）

2. **读产物**：对照 `source-code/{项目}/{项目}-{类型}/{项目}-{类型}-{索引}/`（任务副本，02-round-capture 已从容器导回）的 git 变更（`git diff --stat` + `git diff`，或当前代码）核实模型实际改了什么、和它在轨迹里「宣称改了什么」是否一致（虚假完成判定）。

3. **路线 A — 代码产物质量**（调用 `skills/implementation-reviewer/SKILL.md`）：
   - 传入本轮 User Prompt + 轨迹 + 产物 diff 作为上下文
   - 要求其覆盖 6 维度（Prompt理解度/实现逻辑完整性/验证完整性/会话反馈响应性/跨迭代协调性/代码架构质量）
   - 输出：满意/不满意判定 + 不满意的点 + 过程满意度
   - 第 1、2 轮用挑剔模式（7 角度逐一核查）
   - **以 implementation-reviewer 结论为准**（红线）

4. **路线 B — 对话过程质量**（自行分析，对应 solo 的 10 维度，映射到 cc-solo 五维）：
   - 从轨迹还原：拆解/状态追踪 → 任务规划；thinking 的推理路径/根因定位 → 推理能力；tool_use 的冗余/失败调用/高危操作 → 执行能力；总结声称 vs 实际 → 虚假完成

5. **合成五维**（1-5 + 依据）：

   | 五维 | 主要来源 |
   |------|---------|
   | 交付完整性 | 路线 A（实现逻辑完整性 + 验证完整性 + 架构质量） |
   | 指令遵循 | 路线 A（Prompt理解度 + 会话反馈响应性）+ 轨迹逐条核对约束 |
   | 任务规划 | 路线 B（拆解/状态/歧义求证/阶段总结） |
   | 推理能力 | 路线 B（thinking 推理路径/根因定位） |
   | 执行能力 | 路线 B（tool_use 冗余/失败/高危） |

6. **不满意（过程 + 产物，合成一个字段，必填）**：
   - 格式固定两行（过程在前、产物在后），随五维写入 `{任务}-R{NN}.md`，进提交表「不满意」一列：
     ```
     过程不满意：<过程层面没做好的核心问题；来源=任务规划/推理/执行描述；满意写「无」>。
     产物不满意：<代码/结果层面没做对的核心问题，≤3 条；来源=implementation-reviewer「不满意的点」+交付完整性/指令遵循描述；满意写「无」>。
     ```
   - **逻辑：产物不满意 ⇒ 过程不满意**——产物有问题时过程也必有问题，两条都写；产物满意但过程不满意时，只写「过程不满意」、产物写「无」。

7. **去 AI 化 → 落盘**：合成文本先经 `skills/humanizer-zh/SKILL.md` 去 AI 化（练习无需人工确认，正式再复核），写入 `{任务}-R{NN}.md`。

> 自然语言优先（同 solo）：依据用业务语义描述，禁止堆函数名/代码符号；可列「涉及文件」。

## 🔍 分析自检清单（AI 代打落盘前必勾，红线）

逐项确认后才可写 `{任务}-R{NN}.md`，任一未勾 → 不得落盘：

- [ ] 已读轨迹文件并定位第 N 轮（User Prompt + thinking + tool_use/tool_result + 最终回答），TurnID/SessionID 与 02-round-capture 一致
- [ ] 已核对产物（`git diff`/当前代码）与轨迹里「宣称改了什么」是否一致，虚假完成已判
- [ ] 已调用 implementation-reviewer，其 6 维度（Prompt理解度/实现逻辑完整性/验证完整性/会话反馈响应性/跨迭代协调性/代码架构质量）逐一覆盖
- [ ] implementation-reviewer 的满意/不满意结论 + 不满意的点已采纳（第 1、2 轮走挑剔模式）
- [ ] 过程分析已覆盖 solo 10 维度（prompt理解/目标明确性/推理路径质量/输出质量/任务规划/工具使用/整体流程/高危操作/总结准确性/虚假完成）
- [ ] 五维（交付完整性/指令遵循/任务规划/推理能力/执行能力）各维都有轨迹或产物证据，无「无证据」维度
- [ ] 五维分数 1-5 整数，且与 implementation-reviewer 结论方向一致
- [ ] 分数与依据描述方向一致（4/5 分不得含「未完成/失败/报错/虚假」等失败表述；1/2 分必须写明负面证据，无「低分写得像满分」）
- [ ] 每条描述都能**独立阅读**：不写跨轮次表述（上一轮／前一轮／上轮／上一版），也不写与改动前对比的表述（比改动前／原来／原先／原本／此前）；要说退步或修好，直接陈述现象与现状
- [ ] 「不满意」字段已填（过程不满意 + 产物不满意，满意写「无」），与五维描述一致
- [ ] 已 humanizer-zh 去 AI 化（28 条全查）
- [ ] **全字段无字面代码**：文件路径/文件名/函数名/命令/参数一律改写成业务语义（含「模型回答存档（内部）」「备注（内部）」等不提交字段）
- [ ] **无指向句**：不写「详见 xxx-trajectory.jsonl」（轨迹靠 SessionID + TurnID 定位，指向句只会引入长英文串）

## 评分表（每轮单独打；各 1-5 整数）

> 依据 = **只评估本轮**：前几轮翻车但最后一轮修正 → 前几轮按各自表现打（通常低分），最后一轮按本轮表现单独评（反复自纠磕绊→体感差；高效回归→可高分）。

| 维度 | 考察对象 | 1 | 2 | 3 | 4 | 5 |
|------|---------|-----|-----|-----|-----|-----|
| 交付完整性 | 任务成败/能否跑通/虚假成功 | 完全失败、严重编译报错不可运行/答非所问/极其恶劣虚假成功 | 未达成主要需求、无法运行或较大比例虚假成功 | 勉强达标、明显 Bug 需人工微调/轻微虚假成功 | 基本完美、主要需求达成、极少细节遗漏、无虚假成功 | 一次性完美跑通、主动补全隐性需求、零虚假成功 |
| 指令遵循 | 是否严格遵守用户明确约束 | 彻底无视所有约束/反向执行 | 违背核心指令、需大规模重构 | 遗漏 1-2 个明确负面约束 | 遵循核心+绝大部分次要约束，仅极细微偏差 | 分毫不差、无任何自作主张 |
| 任务规划 | 拆解/状态追踪/歧义求证/阶段总结 | 无头苍蝇、无任何状态、进展不可知 | 盲目写代码、无拆解、状态缺失或失真、遇歧义靠猜 | 有大方向规划但子任务不细、状态明显遗漏 | 拆解总结合理、偶有状态更新不及时 | 拆解极清晰、计划持续更新、歧义主动求证 |
| 推理能力 | 「想」的正确性与性价比 | 需求理解完全错误/严重幻觉/死循环绕圈 | 逻辑混乱、猜答案、过度或不足思考明显低效 | 理解主要任务但忽略部分条件、遇错多次尝试 | 方向正确、较快定位根因、偶忽略次要边界 | 一针见血定位根因一次性修复、思考量与难度匹配 |
| 执行能力 | 「做」的正确性与性价比（toolcall） | 工具严重滥用/缺失、产物不可用 | 大量冗余/失败调用、明显低效 | 较明显冗余调用、整体效率有提升空间 | 少量冗余读取/检索、不影响结果 | 调用精准最小化、一步到位、能批量/并行 |

## 五个「- 描述」硬性要求（质检点）

1. **必须为可核验的具体依据**，不接受「表现一般/基本可用」类笼统表述。
2. 写出具体文件、报错信息或未实现的需求点；判虚假成功时说明「宣称改了什么 vs 实际改了什么」。
3. 指令遵循：列出被违背的约束原文与模型实际行为；给满分写一句「已逐条核对全部约束」。
4. 任务规划：说明拆解/状态追踪在哪一步出问题（不同 Harness 计划工具形态不同，只写计划与状态问题本身）。
5. 推理能力：写清在哪里想错/想偏；涉及思考量时区分过度思考 vs 思考不足。
6. 执行能力：指出具体冗余或失败调用（如被重复读取的文件名、反复失败的命令）。
7. 三要素结构：**触发节点(When)+实际行为(What)+业务影响(Impact)**，最好能指出根因与正确做法（参考 docs/annotate-guide.md §5）。
8. **不用 AI 套话词（红线）**：评价结果里一律不写 `落地`、`模型`、`赋能`、`助力`、`闭环`、`链路`、`复用`、`对齐`、`颗粒度`、`层面`、`体现` 这类空词（完整词表见 `docs/annotate-guide.md` §9）。**指被评测的 AI 时用「它」**；**指 Django 数据模型时写「数据定义」或直接引用 `models.py` 里的类名**。
9. **尽量写成中文，不要写长英文串（红线，实测被打回过）**：避免连续 ≥12 个英文字符的命令/参数/标识符/路径。平台的 B-5「公共长片段」查重按连续字符比对，长英文串在别人的提交里也常见，极易被判「套模板」打回。改写示例见 `docs/annotate-guide.md` §9；短标识（JWT、400、HTTP、SQLite）不受影响。
10. **不写字面代码——覆盖记录文件的所有字段（红线）**：描述里不出现文件路径、文件名、函数名、命令与参数（如 `src/config/deviceCompareMetrics.ts`、`--break-system-packages`），一律改写成业务语义（「设备指标配置预设」「包管理器的强制安装参数」）。**这条不限于五个「-描述」**，同样适用于「模型回答存档（内部）」「备注（内部）」等不提交字段——被查重打回的往往正是这些字段里的路径与命令串，落盘前要一并改写。
11. **不写指向句（红线）**：不写「详见 xxx-trajectory.jsonl」这类指向句。轨迹本身就是提交附件，平台靠 `SessionID` + `TurnID` 定位到轮次，指向句不增加任何信息，还平白引入一长串英文。
12. **描述骨架不得跨任务雷同（红线，实测被打回）**：同一批数据里多条“任务规划-描述”如果用同一句式开头（“动手前建了 N 条任务清单／M 次状态更新／把 N 条都推到已完成／没有废弃／缺口是……”这一套），会被平台按 **B-6 骨架累加雷同**打回，实测相似度 43.8%~46.9% 即判雷同。算法是去掉标点后按连续片段比对：连续 6 字以上算一段，共用片段占两段中较短一段的 40% 以上即命中。写法要围绕本轮真实内容展开，各条描述的骨架互不相同；把描述写长或写短都解决不了，只有换骨架才有效。实测打回见 `docs/reject-reasons.md` §2.1。
13. **描述必须是通顺的完整中文句（实测被打回）**：不得用名词短语堆砌、省略主语或缺谓语来压缩结论（被打回的实例：“十六次改动只读过一次文件，其余依赖对文件的印象，状态粒度偏粗，验证也没有单独立项”“五次命令都在探查，随后两次写入与三次改动结束”）。每句话都要有主语与谓语，主语可以用“它”；写完把每句单独拎出来读一遍，读不通就重写。平台打回建议里会让我们补主谓，思路可用、句子不要照抄——它的示例句用“模型”指被评测的 AI，照抄会把套话词带进评价结果。实测打回见 `docs/reject-reasons.md` §2.2。
14. **要给业务语义的定位信息（实测被打回，与第 10 条平衡）**：说某处有问题时，要写清是哪个页面／哪个接口／哪一段处理／哪一步操作／哪条用例上发现的、哪个字段错了，不能只说“前端取数逻辑有问题”“单测无效”；**同时仍不得写文件路径与英文文件名**——平台打回建议里写的“补充具体的文件名（如 search.js 或 index.wxml）”不能照办，长英文串会被 B-5 公共长片段查重打回，正确做法是把落点翻译成中文业务语义。处理办法与正反例见 `docs/reject-reasons.md` §2.3。实测打回见 `docs/reject-reasons.md`。

## 执行流程

1. 打开 `{RECORD_DIR}/{任务}/{任务}-R{NN}.md`（`{任务}` = 任务 ID = 仓库目录名-类型slug），确认该轮已录入（有 User Prompt/TurnID）；缺 → 先执行 `02-round-capture round N`。
2. **录入方式**（先与用户确认，二选一）：
   - **人工打分**：向用户逐维度索要分数与依据（可一次给齐五维）：
     - 交付完整性 `<1-5>` + 描述（指明文件/报错/未实现点；虚假成功说明宣称 vs 实际）
     - 指令遵循 `<1-5>` + 描述；任务规划 `<1-5>` + 描述；推理能力 `<1-5>` + 描述；执行能力 `<1-5>` + 描述
     - 其他问题（未覆盖五维的其他问题，无可填「无」）
     → **原样录入**到数据文件对应字段，不改写措辞、不替用户补内容。
   - **AI 代打（练习阶段默认）**：按上「分析调用链路」走完 读轨迹 → 读产物 → 路线A(implementation-reviewer) → 路线B(过程分析) → 合成五维，再**先经 `skills/humanizer-zh/SKILL.md` 去 AI 化**后落盘（练习阶段无需人工确认；正式交付再人工复核）。
3. **机械校验**（只校验，不改写/不改分）：
   - 分数为 1-5 整数；五个描述均非空
   - 描述过短/疑似笼统（如仅「表现一般」「还可以」等字样）→ 提示人工按硬性要求补充
   - **方向一致性（红线）**：分数 ≥4 但描述含强失败词（未完成/失败/没改/报错/虚假等），或分数 ≤2 但描述无负面证据 → 必须修正到一致，否则不得落盘
   - **评分-描述一致性（ai 代打必核）**：给 4+ 时描述须体现**真实**拆解/状态回报/纠错证据，不得写「无计划/无状态记录」这类与分数矛盾的表述；交付完整性避免「全部实现」绝对表述，有未验证项写「主体已实现，XX 尚未验证」；描述中文件数/行数/调用数要对照真实产物（`git diff --stat`、轨迹 tool_use）；写到的验证（tsc/构建/冒烟）须在轨迹/产物有据——见 docs/annotate-guide.md §9。
   - **独立阅读（红线）**：描述里不得出现 ① 跨轮次表述（上一轮／前一轮／上轮／之前那轮／上一版）、② 与改动前对比的表述（改动前／修改前／比之前／原来／原先／原本／此前）。两者都会让描述依赖别的轮次或改之前的状态，平台按「无法独立阅读」返修；要说退步或修好，直接陈述现象与现状（写「正确选项不再高亮」，不写「比改动前退了一步」）。`build_eval_result.py` 用 `CROSS_ROUND` + `PAST_COMPARE` 检查，五个「-描述」命中即 error 阻塞提交。
   - **AI 痕迹检查**：AI 起草内容须确认已去 AI 化且无残留痕迹（`——`、反引号、`「」`、`→`/`⇒`/`=>`/`->`、英文直引号等，humanizer-zh 强制项）
   - **一键自查**：`python scripts/cc-solo/check_round_files.py --project {项目}`——分数、描述、词表、符号、跨轮次与前后对比、轨迹文件一次跑完，有 error 返回码 1，可直接当导出前门禁；下一轮提示词另跑 `python scripts/cc-solo/lint_round_prompt.py --project {项目}`（查「只写现象、不分条、无改法措辞」）
4. **判定 + 生成下一轮提示词**：
   - 满意且目标达成 → 结束本任务。
   - **产物不满意**（implementation-reviewer 判不满意，或交付完整性/指令遵循 ≤2；判据：代码漏洞 / 功能未实现 / 实现不合理）→ 按下方「下一轮提示词生成」拆分不满点、生成下一轮提示词并写 prompt 文件。**仅过程不满意、产物满意时不生成下一轮提示词**。
   - N+1 > 10 → 强制结束，开新任务。

## 下一轮提示词生成（产物不满意后）

> ⚠️ **第二轮及以后的提示词只描述现象，不写怎么改（硬性）**：用真实用户的口气写「我做了什么、看到什么、哪里不对劲、造成什么影响」，**不要**写实现指引——不写「改成……」「先……再……」「加个判断」「抽成公共件」「补一条迁移」这类改法，也不要替它定方案（身份校验怎么做、缓存怎么加都不写）。**不要分条列举**（不写 1、2、3、也不写「第一……第二……」），用连续的几段话把现象讲清楚，让它自己去定位和设计修法。首轮提示词不受这条限制：首轮是需求，本来就要写清要什么。

> ⚠️ **口吻要像真实用户报问题，不带客套（硬性）**：**不写「麻烦」「请」「帮忙」「谢谢」这类客气话**，也不用「辛苦你了」「不知道方不方便」这类先征询的句式。客套话是 AI 起草的典型痕迹，真实用户报 bug 时语气是直的。
>
> ⚠️ **不要求对方验证、不要求回报结果（硬性，2026-09-12 口径）**：提示词里**一律不写**「跑一遍」「走一遍」「各点一遍」「起服务试一下」这类要对方去验证的话，也**不写**「把结果发我」「结果发回」「告诉我结果」这类要回报的话。只把用户看到的现状与影响讲清楚就收尾；要什么证据由标注侧自己取，不在提示词里指派。此前已发出的提示词不追改，`lint_round_prompt.py` 对这类写法记 error。
>
> ⚠️ **不得自曝未验证（硬性）**：prompt 里**不许出现**「我没在浏览器里跑过」「我是按代码推的」「我只对着代码看过」这类表述——它等于承认这份报告来自静态阅读而不是真实使用，既暴露标注方没做实测，也会让被评测模型判定为推断而非事实（它可能反过来质疑问题是否存在）。
> 注意与本文件 §10 第 3 条的区别：**「缺浏览器实测」要写进五维的「-描述」**（那是标注证据链的必需交代），但**不能写进给模型看的下一轮 prompt**。前者是给质检看，后者是给模型看，两者口径相反。

> ⚠️ **提示词本身也要避开两类词（硬性）**：下一轮 prompt 会原样成为提交表里的 `User Prompt` 列，所以 ① 不写「本来／原本／原先／原来／此前／比改动前／上一轮／前一轮」这类前后对比与跨轮说法（`build_eval_result.py` 的 `PAST_COMPARE` + `CROSS_ROUND` 在 `user_prompt` 列记 warn）；② 不写文件路径、函数名、命令（如 `src/config/xxx.ts`）——真实用户报 bug 只会说页面和看到的现象。
> 写法对照：不写「这个面板原本还想放到别的地方用」，写「这个面板我还想放到别的地方比别的对象」。（从轨迹取回的人工原文不改写，此项只约束 AI 起草的新提示词。）

1. **拆分不满意点**：从 implementation-reviewer「不满意的点」+ 五维里「交付完整性-描述」「指令遵循-描述」+「其他问题」，提取「代码漏洞 / 功能未实现 / 实现不合理」层面的**现象**（业务语义，禁代码符号）。
2. **保证预计 ≥2 文件**：标注每个现象落在哪个文件/模块；若集中在 1 个文件 → 补一条跨文件的现象（如「改完之后依赖它的另一处也没跟着变」）。
3. **生成提示词**：开头固定加「**修复bug：**」，接着用 **2~4 个连续段落**描述现象（在做什么 → 看到什么 → 影响是什么），语气就是用的人来报问题；**不列编号、不写改法、不写实现建议、不写「应该」**。**结尾把现象讲完就收**——不写任何要求对方跑一遍、验证一遍或回报结果的话（见上面「不要求对方验证」那条硬性口径）。
4. **去 AI 化**（`skills/humanizer-zh`）→ 写 `{RECORD_DIR}/{任务}/{任务}-R{NN+1}-prompt.md`（NN+1 = 下一轮）。
5. **输出给用户确认**，确认后贴进 Claude 会话做下一轮。
6. **多轮批量（可选）**：不满点多时拆成多份 `-R{NN+1}-prompt.md`、`-R{NN+2}-prompt.md`…，每份都必须涉及 ≥2 文件的现象。

### 正反例（同一处问题）

- ❌ 写改法 + 分条：「1. 搜索是前端过滤，改成后端按关键词查、带分页，前端只渲染当前页。2. 角色下拉取了全部角色，改成跟有台词的角色取交集。」
- ✅ 只写现象 + 连续段落：「搜索页打开很慢，看下来是进页面就把全部台词拉了下来在前端过滤，台词一多首屏就顶不住，用户说的只能一页页翻这个问题也没真解决。角色筛选的下拉里还有一个选项，选它永远是空的，那个角色底下根本没有台词。」

### 正反例（同一处问题 · 口吻与自曝）

- ❌ 客套 + 自曝 + 要求验证：「麻烦你把这几个页面都跑一遍看看，把结果发我。另外说一下，我这一轮没在浏览器里实际点过，上面是按代码推的，可能有出入。」
- ✅ 直接 + 只讲现象、不派活：「这几种组合我都点过一遍，标出来的那几行都是空的，看着跟筛选条件对不上。」

## 路径规则

```
任务记录目录（R0N 模型）：{RECORD_DIR}/{项目}/{项目}-{类型}/{项目}-{类型}-{索引}/
第 N 轮数据（打分写入此处）：…/{项目}-{类型}-{索引}-R{NN}.md
第 N 轮轨迹切片：…/{项目}-{类型}-{索引}-R{NN}-trajectory.jsonl
任务副本：{REPO_BASE_PATH}/{项目}/{项目}-{类型}/{项目}-{类型}-{索引}/
其中 {项目}-{类型}-{索引} = 任务名（如 app-12-bugfix-01）。
```

## 注意事项

1. **去 AI 化门槛**：AI 起草的依据/分数说明无论在练习还是正式，落盘/投递前都须先经 `skills/humanizer-zh/SKILL.md` 去 AI 化，且**须执行其完整流程（28 条规则全查），不得只手动删符号/避关键词**（练习阶段无需人工确认，正式交付补人工复核）；人工撰写的原文不得用 AI 改写。
2. 每轮独立评分：不得因后续轮次修复给前几轮补高分。
3. 只评价模型自身能力问题，不写环境/网络波动导致的请求失败。
4. AI 起草的依据必须可核验（真实轨迹/产物证据），不得脱离依据编造；**必须读轨迹 + 调用 implementation-reviewer（红线）**，最终分数与文字由人工确认。
5. 若目标轮次已有打分内容 → 不覆盖，提示用户确认后由人工决定是否修正。
6. 机械校验发现的问题只提示，最终由人工（专家/TPM）复核。
