# 高难度 Web Dev 长程任务数据采购需求 Draft

# 背景与目标

为了评估和提升 agent 模型在 Web Dev 场景下的真实工程能力，我们希望采购一批高质量 Web Dev 长程任务数据。每条任务应模拟真实前端开发需求：agent 从任务说明、项目初始代码、视觉参考图、mock data 和工具约束出发，完成页面或功能开发，并通过自动化测试、Browser/截图交互验证验收项目的质量。

本批数据重点不是普通社媒 prompt 或简单页面生成，而是更接近真实复杂前端项目的长程任务：需求复杂、视觉标准高、交互链路完整、可通过浏览器工具观察和自我修复，同时 SOTA agent 在合理预算内应能基本完成，不能是当前模型完全不可解的开放题。

# 数据要求

## 任务标签体系

每条任务都需要按现有多维表格标签体系进行标注。

|字段|填写方式|可选标签|
|---|---|---|
|类目树标签（单选）|每题必须选择 1 个主类目|内容型应用：编辑器 / 内容管理；<br>内容型应用：社区 / 信息流 / 内容展示；<br>工具型应用：配置工具 / 内部工具；<br>工具型应用：低代码 / 页面搭建器；<br>游戏 / 实验性应用：Web 游戏 / 交互实验；<br>交互型应用：复杂交互页面；<br>交互型应用：可视化 / 数据看板；<br>展示型页面：作品集 / Showcase/Demo；<br>展示型页面：品牌官网 / 营销页 / 活动页；<br>电商 / 交易应用：O2O 服务 / 聚合平台；<br>电商 / 交易应用：在线商城 / 独立站；<br>业务型应用：SaaS / 业务平台；<br>业务型应用：中后台 / 管理系统；其他。|
|Arena标签（多选）|每题可选择多个能力/风格标签|ui；creative；visualize；game；retro；clone；animation；3d；map；e\-commerce；dashboard；whimsical。|
|Prompt类型|沿用现有表格口径|前端/全栈|

例如：一个带地图筛选、商家卡片、路线规划和订单入口的 O2O 应用，主类目可标为“电商 / 交易应用：O2O 服务 / 聚合平台”，Arena 标签可标为 ui、map、e\-commerce、visualize。

本期不接受只有一句自然语言需求、无工程上下文的普通 prompt；不接受纯静态落地页，除非有高质量视觉参考和明确响应式、动效、可访问性要求；不接受依赖外部登录、付费 API、不可控实时数据或无法稳定复现的第三方服务；不接受主要靠审美主观判断、缺少可验收标准的任务。

## 难度要求

本批数据只采购高难度 Web Dev 长程任务。

高难度任务指长程、高复杂度、强工程约束的 Web Dev 任务，通常涉及多页面、多模块、复杂视觉与交互、现有项目改造、Playwright/MCP 工具验证，以及 agent 多轮观察、截图、自我修复和测试闭环。

|不纳入范围|原因|
|---|---|
|轻量页面或单一功能实现|无法有效评估长程工程能力|
|普通单页应用，仅有基础状态管理、表单、筛选或本地存储|复杂度不足，区分度有限|
|缺少浏览器验证、截图输入或工程上下文的普通 prompt|无法形成可复现、可观察的 benchmark 任务|
|不可验收、不可运行、主要依赖主观审美或外部不可控资源的任务|无法稳定评测|
|SOTA agent 在合理预算内无法完成核心链路的任务|不满足可解性要求|

## 难题准入标准

本批任务中的“难”，不等同于 prompt 更长、功能更多或视觉描述更华丽，而是指任务必须同时对 agent 的产品拆解、工程实现、视觉理解、浏览器观察、调试修复和证据化验证形成压力。

简单说，一道合格难题应该迫使 agent 进入“理解需求 → 修改工程 → 运行页面 → 截图观察 → 发现问题 → 修复 → 再验证”的闭环；如果不需要这个闭环也能完成，它就不算本批要采购的难题。

一条任务只有满足以下准入标准，才可视为高难度 Web Dev 长程任务：

1. **非局部工程改动：**任务不能只改一个页面或一个组件。应涉及多个模块、多个页面、共享状态、路由、数据流、组件体系或现有代码结构调整。agent 需要理解项目结构后再做实现。

2. **复杂约束耦合：**任务中至少存在 3 类相互影响的约束，例如视觉还原、交互状态、数据规则、响应式、错误处理、性能、可访问性、测试要求。完成其中一项不能破坏另一项。

3. **视觉输入不可省略：**任务应包含截图、设计稿、竞品参考或现有页面截图。agent 需要根据视觉输入理解布局、层级、间距、动效、组件状态和整体质感，而不是只根据文字生成普通 UI。

4. **浏览器工具是必要路径：**任务必须需要 Playwright/MCP/browser 工具参与验证。仅靠静态代码阅读无法判断是否完成。agent 需要打开页面、执行交互、截图、检查 console，并基于观察结果修复问题。

5. **存在多状态验收：**不能只验收默认页面。任务应覆盖至少 4 类关键状态，例如加载态、空态、错误态、完成态、hover/focus 态、编辑态、移动端态、交互后状态。

6. **SOTA 可解但不轻松：**最新 SOTA agent 在合理预算内应能完成核心链路，但仍可能在视觉细节、边界状态、测试覆盖或工程质量上失分。若 SOTA 无法完成核心链路，任务应改写或剔除；若普通 agent 一次即可轻松完成，也不应纳入。

# 最低数据格式要求

每条数据必须同时交付以下三部分。

## 任务资产

- `task.md`：完整用户需求，包括背景、目标、功能要求、交互要求、视觉要求、约束条件、交付标准。

- `metadata.json`：至少包含 `task_id`、`title`、`category_tags`、`required_tools`、`annotator`。

- `starter/`：初始项目代码。可以是空项目、半成品项目或需要修改的现有项目，但必须能本地启动。

- `assets/`：截图、参考图、图标、图片、字体说明、mock 数据等任务所需素材。

- `mock-data/`：任务需要的数据文件或 mock API 数据；不允许要求 agent 自行臆造关键业务数据。

- `README.md`：说明启动方式、测试方式、目录结构、已知限制。

## Agent 执行环境

每条任务必须能在标准 Web Dev agent 环境中稳定运行。默认不强制提供 Dockerfile，但必须提供足够清晰、可复现的本地运行说明；只有当任务依赖特殊系统库、浏览器能力、原生模块、图形/音视频处理、3D 渲染或其他非标准环境时，才建议额外提供 Dockerfile。

- 明确 Node\.js 版本、包管理器和 lockfile，例如 `package-lock.json` / `pnpm-lock.yaml` / `yarn.lock`。

- 项目依赖需通过 lockfile 固定，不允许缺失 lockfile 或依赖漂移。

- 项目可通过固定命令安装和启动，例如 `npm install && npm run dev` 或 `pnpm install --frozen-lockfile && pnpm dev`。

- 如使用 Playwright，需提供浏览器安装、测试运行和截图输出说明。

- 若使用skills/任何MCP，需要在 readme 或 assets下体现。

- 不依赖供应商私有服务、个人登录态或不可访问资源。

- 如果依赖 mock API、静态数据或本地服务，必须在仓库内提供启动方式。

- 如有评测产物，统一输出到 `submission/` 或 `artifacts/`。

## SOTA产出物与轨迹

# 可选提供

每条任务可选提供 rubric 级验收标准，建议 10\-20 个叶节点。Rubric 是最终判断任务质量的核心依据，应覆盖功能、视觉、交互、工程质量、边界状态和测试证据。

浏览器、Playwright、MCP、截图、DOM snapshot、console 检查等不作为独立交付模块，而是 rubric 的证据来源。每个核心叶节点应尽量说明需要什么证据来判断是否通过。

|Rubric 维度|验收重点|可能的证据来源|
|---|---|---|
|功能完整性|核心功能是否实现，数据流是否正确|Playwright 交互记录、DOM/text assertion、测试日志|
|交互完整性|hover、点击、输入、筛选、拖拽、保存、错误处理等是否可用|浏览器操作记录、关键状态截图、DOM snapshot|
|视觉完成度|布局、层级、间距、色彩、字体、动效、响应式是否达到参考标准|参考截图、最终截图、人工视觉审查或 LLM judge|
|工程质量|组件拆分、状态管理、类型安全、可维护性、无明显硬编码|代码审查、lint/typecheck、单元测试|
|边界状态|空数据、长文本、加载失败、移动端、小屏幕、异常输入|多状态截图、Playwright scenario、错误态日志|
|测试与证据|是否提供必要的运行记录、截图、console 检查或测试结果|测试输出、console/network 检查、artifacts 目录|

每个叶节点应包含 `criterion`、`weight`、`grader_spec` 和 `evidence_required`。可接受的 `grader_spec` 类型包括 `playwright_assertion`、`screenshot_review`、`dom_assertion`、`unit_test`、`llm_judge`、`manual_review`。确定性检查优先用于天然适合自动化验证的叶节点，但不强制每题提供完整 Playwright 脚本。

**优先级排序：**任务资产 \+ 可运行环境 \> SOTA 轨迹与交付物 \> Rubric / Acceptance Criteria；浏览器/MCP/截图证据作为 rubric 的取证方式。

# 重要提示

- 高端视觉任务必须有截图输入或明确视觉参考，不接受只写“高级、现代、美观”。

- 允许 LLM 辅助生成初稿，但最终任务、AC 和 rubric 必须由高级前端标注员 review。

- 任务内容、rubric 和参考截图需保持私有，不得公开发布或被搜索引擎索引。

- 视觉参考可以来自产品截图、设计稿、竞品页面或文章图，但需要说明参考用途：布局、视觉风格、动效、交互状态或信息架构。

- 不应要求照抄竞品品牌资产；应抽象其布局、交互和视觉语言。

# 质量控制

供应商负责自己的生产流水线和内部 QC。我方设置以下质量闸门，任一不过即阻塞交付。

1. **可运行性：**项目能在干净环境中安装、启动、访问页面，并能运行基础测试。

2. **任务完整性：**需求、素材、mock data、约束和验收标准齐全，agent 不需要猜核心业务逻辑。

3. **视觉可验收性：**高端视觉任务必须提供参考截图，并说明哪些部分要求高保真、哪些只要求风格对齐。

4. **Rubric 有效性：**验收标准能区分好坏结果，不允许用“按钮存在”“页面能打开”等低价值叶节点充数。

5. **可解性：**至少一次 SOTA agent 运行证明任务不是完全不可解；核心链路无法完成的任务需改写或剔除。

6. **无污染风险：**任务、rubric、参考答案不应来自公开 benchmark，不能将完整答案暴露在 prompt 或 starter 中。

# 标注人画像要求

标注员需具备真实前端工程经验，优先满足以下条件：

- 熟悉 React / Vue / TypeScript / CSS 工程化。

- 能独立实现复杂页面、状态管理、组件拆分和 Playwright 测试。

- 有设计还原、数据看板、复杂表单、动画或中后台经验。

- 能判断什么是“高级前端完成度”，而不是只检查功能是否存在。

- 能使用 agent / vibe coding 工具，并理解 agent 在长程任务中的常见失败模式。

供应商需披露标注员构成、每条任务投入工时、review 流程和返工机制。
